# AGENTS.md — Uni Space / «Цифровой деканат будущего»

> Постоянные инструкции для coding-агентов в этом репозитории. Этот файл описывает **процесс работы**, а не заменяет продуктовые, архитектурные и технические спецификации.
> На момент создания правила относятся к проекту **до реализации**: наличие целевой структуры и команд нельзя предполагать.

## 1. Контекст и источники истины

Uni Space — адаптивный веб-кабинет для студентов, позже — преподавателей, сотрудников и администраторов. Ближайшая цель — рабочий конкурсный **MVP 1**; MVP 2 и Extended не должны его блокировать.

Перед каждой задачей читай **релевантные разделы**:

1. [`docs/PRD.md`](docs/PRD.md) — функциональность, ID `REQ-*`, приоритеты, этапы, продуктовые правила и критерии приёмки.
2. [`docs/ARCHITECTURE.md`](docs/ARCHITECTURE.md) — утверждённый стек, структура, слои, auth, API, транзакции, деплой и технические решения.
3. [`docs/DB.md`](docs/DB.md) — **единственный источник** схемы таблиц, ключей, связей и ограничений данных; это не `DATA_MODEL.md`.
4. Файл назначенной задачи (когда backlog будет создан) и существующий код/тесты.

**Разделение ответственности:** PRD отвечает на «что», Architecture — на «как устроено», DB — на «как хранятся и связываются данные». Точный контракт API **после реализации** — генерируемый FastAPI OpenAPI по `/api/openapi.json`; перечень путей в Architecture пока планируемый.

Не объявляй черновики и `TBD` окончательными решениями. При конфликте документов, необходимости отступить от принятой схемы или существенном неразрешённом `TBD`: явно укажи проблему и варианты, не реализуй спорное решение молча. Текст отдельной задачи не отменяет архитектурные/предметные инварианты.

## 2. Текущая стадия и границы релизов

- **MVP 1:** логин/логаут, собственный профиль, дневное и недельное расписание с изменениями, успеваемость/сессия, каталог услуг, реальная подача и сохранение статуса заявки, новости, внутренние уведомления, адаптивность, изоляция данных. Учебные данные могут быть заранее подготовлены, но читаются из PostgreSQL; заявка должна реально записываться в БД.
- **MVP 2:** четыре роли и полномочия, журнал, оценки и посещаемость с аудитом, редактор расписания и проверка конфликтов, обработка заявок, вложения и PDF, смена/сброс пароля, ручное изменение академического статуса сотрудником с аудитом.
- **Extended:** только по отдельной задаче. Не добавляй функции «заодно».
- Приоритет `P0` сам по себе не перемещает требование из MVP 2 в MVP 1: смотри колонку «Этап» в PRD.
- Не создавай административный CRUD и модели/таблицы для будущих релизов раньше необходимого.

## 3. Зафиксированный технический стек

- **Frontend:** React + TypeScript + Vite; Tailwind CSS + shadcn/ui; React Router; TanStack Query + Fetch API.
- **API-контракт:** REST/JSON `/api/v1`; Pydantic 2; генерируемый FastAPI OpenAPI и TypeScript-типы из OpenAPI, без ручного дублирования контрактов.
- **Backend:** Python + FastAPI; SQLAlchemy 2 с **синхронным** `Session` и psycopg 3; Alembic.
- **База данных:** PostgreSQL (одна общая реляционная БД).
- **Безопасность:** Argon2id для паролей, PyJWT с фиксированным `HS256` для access-токенов.
- **Тесты:** pytest + HTTPX (backend); Vitest + React Testing Library (frontend); Playwright для E2E по мере появления.
- **Развёртывание:** Docker Compose + Nginx, один origin для SPA и `/api`.

Это **проектные решения**, а не подтверждение уже установленных пакетов/созданных файлов. Не подменяй стек, не добавляй микросервисы, `AsyncSession`, новый ORM, отдельные БД по ролям или сложные абстракции без согласования. Конкретные версии фиксируй lock-файлами при инициализации.

## 4. Архитектура и ответственность слоёв

**Модульный монолит:** `routers → services → SQLAlchemy → PostgreSQL`. **Отдельного `repositories/` слоя нет и добавлять его не нужно.**

- `backend/app/routers/`: HTTP, Pydantic-схемы, коды ответа, Depends; без бизнес-алгоритмов и длительных запросов.
- `backend/app/services/`: бизнес-сценарии, запросы, объектные права, транзакции и согласованность данных.
- `backend/app/models/` и `schemas/`: ORM и API-представления — разные сущности.
- `backend/app/dependencies/`: сессии БД и общие проверки пользователя/прав; `core/`: конфигурация, безопасность и инфраструктура.
- **Одна транзакция на бизнес-сценарий.** Верхнеуровневый сервис владеет commit/rollback; вспомогательные функции не коммитят посреди операции, router не дублирует commit/rollback. Специальные многошаговые сценарии (reuse refresh, PDF в MVP 2) выполняются по Architecture/DB.
- `frontend/src/app/`: провайдеры и роутинг; `pages/`: композиция страниц; `features/`: логика по функциональным областям; `layouts/`: каркас; `shared/`: общие компоненты, HTTP-клиент, OpenAPI-типы.
- На production Nginx обслуживает SPA и проксирует `/api`; backend и PostgreSQL не выставляются напрямую в интернет.

Структура из `docs/ARCHITECTURE.md` — **целевая**. Создавай каталоги только по мере необходимости; не генерируй пустые модули ради соответствия дереву.

## 5. Инварианты модели данных

Вместо дублирования SQL-спецификации следуй `docs/DB.md`. Особенно важно:

- Основные PK — `BIGINT ... IDENTITY`, FK — `BIGINT`; время хранения меток — `TIMESTAMPTZ` UTC, даты учебных событий отображаются в университетском часовом поясе.
- У студента ровно **одна актуальная группа** в `students.group_id`; отдельной истории членства в группах нет.
- `course_offerings` отделены от справочника `disciplines`; одна пара может принадлежать нескольким группам; занятие (`lessons`) и оцениваемая работа (`assessments`) — разные сущности.
- `assessment_groups` хранит назначение работы группе, включая её дату; `0` баллов не равен отсутствию результата.
- Для экзамена/дифференцированного зачёта оценка **2–5**, для зачёта — `passed=true/false`; отсутствие результата не означает задолженность.
- `applications.review_status` и `applications.document_status` независимы; `form_data JSONB` только для полей конкретной услуги, а не для владельца/статусов.
- `news`, `teacher_announcements` и `notifications` — разные сущности; уведомления имеют адресата и не предоставляют обход прав через ссылку.
- Схему меняй только через Alembic с учётом ограничений, индексов, обратной совместимости и этапа выпуска. Не создавай SQL-триггеры и дополнительные таблицы «на всякий случай».
- Для MVP 2: версии нужны у `lessons` и `applications` с атомарным `UPDATE ... WHERE version = ...` и ответом `409`; **для оценок отдельные версии не вводятся** — изменение и аудит в одной транзакции. Максимум работы блокируется после первого результата. PDF неизменяем и не выдаётся дважды. Академический статус **не меняется автоматически** при одобрении заявления.

## 6. Авторизация, безопасность и разделение данных

Соблюдай `docs/ARCHITECTURE.md` §6 и `docs/DB.md` §3.1; не упрощай их до «JWT в localStorage».

- **Access:** JWT `HS256`, только в памяти React (не `localStorage`, не `sessionStorage`, не URL). Проверять подпись, срок, обязательные claims `exp/iat/iss/aud/sub/sid/jti/token_type`, текущего пользователя и действующую сессию **на каждом защищённом API-запросе**. Время access 10 минут — предварительное.
- **Refresh:** случайный opaque token (не JWT), только `HttpOnly` cookie с `SameSite=Lax`, `Path=/api/v1/auth`, без `Domain`; `Secure` в production. Хранить в БД только SHA-256-хеш. Абсолютный срок сессии 7 дней — предварительный; ротация его не продлевает.
- **Ротация:** блокировка `auth_sessions` через `SELECT ... FOR UPDATE`, повторная проверка токена после получения блокировки; reuse старого токена отзывает всю сессию, и отзыв фиксируется **до** ответа с ошибкой. Координировать refresh между запросами и вкладками, не делать слепых повторов.
- **Logout:** по refresh cookie, даже без действительного access; очищать cookie и клиентский персональный кеш. При reload — восстановление через refresh, не через постоянное браузерное хранилище. Не допускать показа данных прежнего аккаунта при смене пользователя.
- **Origin/CSRF:** проверять `Origin` для изменяющих auth-маршрутов (`login`, `refresh`, `logout`); SPA и API — один origin в production.
- **Права:** роль и полномочия устанавливаются сервером, **не** из `student_id` в запросе и не только из UI. Свой профиль, оценки, уведомления и заявки доступны исключительно владельцу; неизвестные и чужие идентификаторы не должны раскрывать существование чужой записи (см. правила `401/403/404` в Architecture). Для сотрудников разрешения задаются явно и отдельно для каждого действия, не по факту роли администратора.
- Никогда не сохраняй пароли в открытом виде, секреты, сырые токены или чувствительную информацию в Git, frontend и логи. Не использовать реальные личные/учебные данные или закрытые системы вуза.
- Два тестовых студенческих аккаунта должны иметь **разные** профили/данные; демонстрационные пароли не помещать в миграции и production-код открытым текстом.

## 7. Правила UX и поведения MVP 1

- Старт студента — **расписание текущего дня**. Основная навигация: расписание, успеваемость, услуги и документы, новости; профиль — в меню, уведомления — через колокольчик.
- Расписание: день/неделя, времена, преподаватели и аудитории, явно видимые отмены и переносы; прежняя перенесённая/отменённая пара не занимает время.
- Сессия находится **внутри успеваемости**; новости университета не смешиваются с персональными уведомлениями.
- Оформление заявки должно проводить реальный API-запрос и сохранять данные/статус в PostgreSQL после reload и повторного входа. В MVP 1 достаточно одной работающей услуги, PDF относится к MVP 2.
- Адаптивность от **360 px**; desktop sidebar, mobile burger navigation; без критической горизонтальной прокрутки. Учитывай loading, empty, error, success, доступность с клавиатуры и обозначения не только цветом.
- Видимая пометка **«Конкурсный прототип / неофициальный сервис»**; без официального логотипа вуза. Только вымышленные данные.
- Хостинг должен быть доступен из России без VPN до **28 ноября 2026 года**; сам факт доступности проверяется отдельно, не предполагается.

## 8. Протокол выполнения `TASK-XXX`

1. Найди точное описание задачи и проверь её `REQ-*`, этап, зависимости, область изменений и критерии приёмки. Если задачи/реестра ещё нет — **не придумывай содержание по номеру**.
2. Прочитай применимые разделы `docs/PRD.md`, `docs/ARCHITECTURE.md`, `docs/DB.md`; изучи реальные файлы, историю изменений и текущие тесты.
3. Проверь зависимости и конфликты с документацией. Если изменение требует решения `TBD` или отступления от утверждённого инварианта — обозначь блокер и предложи варианты.
4. Реализуй **минимальное законченное изменение** в рамках задачи. Не переделывай соседние подсистемы, не добавляй необязательные зависимости и не делай рефакторинг «заодно».
5. Добавь/обнови тесты, включая негативные проверки авторизации и разграничения прав для защищённых данных. При изменении API согласуй backend-схемы, OpenAPI-типы frontend и тесты; при изменении БД добавь миграцию.
6. Запусти реально доступные проверки. Просмотри diff: нет ли лишних файлов, секретов, сломанных контрактов, незапланированного изменения UX или данных.
7. Отчитайся по §10. Не помечай задачу выполненной, пока не проверены критерии приёмки.

Не меняй чужие незакоммиченные правки. **Запрещены без прямого разрешения:** `git reset --hard`, force-push, уничтожение данных, разрушительные миграции, публикация/деплой, изменение production-секретов. Commit/push/merge и статусы задач — по явному указанию или согласованному процессу репозитория.

## 9. Команды, тесты и проверка среды

Сейчас репозиторий содержит документацию, но **приложение и команды запуска ещё не созданы**. Не выдавай предполагаемые команды за проверенные.

- Когда появятся `frontend/package.json`, `backend/pyproject.toml`, `compose.yaml`, `README.md`, прочитай их и зафиксируй **фактические** команды установки, запуска, тестов, линтинга и сборки.
- Backend: pytest/HTTPX, интеграционные тесты БД, проверка Alembic; сценарии блокировок, уникальности и конкурентных операций проверяй на **PostgreSQL**, не считай SQLite эквивалентом.
- Frontend: Vitest/Testing Library, проверка типов и сборки; E2E через Playwright, включая mobile viewport 360 px, если инструмент настроен.
- Обязательные проверки MVP 1: доступ A к данным B закрыт прямыми API-запросами; неверный/истёкший токен и отзыв сессии; refresh/logout/reload; разделение персонального кеша; заявка сохраняется после повторного входа; два разных тестовых аккаунта; мобильные сценарии.
- Отсутствующий скрипт, сервис, тест или деплой **не** считаются успешно проверенными. Укажи, что именно и почему невозможно выполнить.

## 10. Отчёт агента и Definition of Done

Отвечай заказчику **по-русски**, технические идентификаторы оставляй как в коде.

**Отчёт по задаче:**
1. ID задачи, связанные `REQ-*`, статус: выполнено / частично / заблокировано.
2. Что изменено: файлы и краткая суть.
3. Что проверено: **точные** команды, результаты тестов, ручные сценарии; что не проверено.
4. Риски/решения: допущения, `TBD`, известные проблемы, расхождения.
5. Что нужно для приёмки и следующая зависимая задача.

**Готово** означает: выполнены критерии задачи и применимые требования PRD; архитектура и модель данных соблюдены либо изменение согласовано; тесты добавлены и запущены где возможно; нет утечек данных или секретов; затронутые сценарии работают на 360 px; diff ограничен задачей. **Окончательная приёмка — за пользователем.** Не заявляй «всё работает» без фактической проверки.
