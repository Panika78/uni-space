# AGENTS.md — Uni Space

Инструкции для coding-агентов. Этот файл регулирует **процесс работы**, а не дублирует спецификации проекта.

## Источники истины

- `docs/PRD.md` — функциональные требования (`REQ-*`), этапы и критерии приёмки.
- `docs/UI_UX_SPEC.md` — согласованные правила интерфейса и адаптивности; не меняет функциональные требования и этапы PRD.
- `docs/ARCHITECTURE.md` — стек, структура проекта, безопасность и архитектурные решения.
- `docs/API.md` — принятый контракт MVP 1: маршруты, схемы, ошибки и клиентское поведение; имеет приоритет над предварительным перечнем API в архитектуре.
- `docs/DB.md` — модель данных, связи, ограничения и правила целостности.
- `docs/AUTH.md` — реализованная серверная авторизация, её конфигурация и требования безопасности.
- Описание текущей задачи — цель, границы, зависимости и ожидаемый результат.
- `README.md` — фактическое состояние проекта, команды запуска и проверки.

Перед работой читай **релевантные разделы**, а не пересказывай все документы. Основные спецификации приняты: их согласованные положения обязательны, а issue уточняет объём задачи, но не переопределяет спецификации молча. При конфликте требований или решении, помеченном `TBD`, сообщи о проблеме и не принимай существенное решение без согласования. Не считай всю целевую структуру уже реализованной: сначала исследуй существующие файлы.

## Границы работы

- Приоритет — **MVP 1**. Не реализуй MVP 2 или Extended без отдельной задачи. `P0` не меняет этап выпуска, указанный в PRD.
- Следуй утверждённым архитектурным решениям; не заменяй стек, модель данных или систему авторизации по своему усмотрению.
- Изменяй только то, что необходимо для текущей задачи. Не добавляй абстракции, зависимости и рефакторинг «заодно».
- Backend — источник истины для прав доступа и бизнес-правил. UI не заменяет серверные проверки.
- Используй только вымышленные данные. Не коммить секреты, реальные персональные данные и учётные данные.

## Соглашения об именах и терминологии

- Идентификаторы, имена файлов, веток, сообщения коммитов и заголовки PR — **на английском**; пользовательские тексты, отчёты и описания PR — на русском. Используй термины из PRD/DB: `student`, `application`, `lesson`, `assessment`, `course_offering`. Не вводи параллельные названия вроде `ticket` вместо `application`.
- Называй функции **действие + объект**, а не по технической реализации: `get_student_profile`, `list_student_applications`, `submit_application`; в TS — `getStudentProfile`, `listStudentApplications`, `submitApplication`. Имя описывает результат, а не способ работы.
- Значения глаголов: `get` — один объект, `list` — коллекция, `create` — создание, `update` — изменение, `delete` — удаление, `submit`/`approve`/`revoke` — бизнес-действие. Различай создание записи и перевод её в другое состояние; не называй их одинаково.
- Для проверок: `is_*`/`has_*`/`can_*` возвращают `bool` / `boolean`; `validate_*` проверяет входные данные; `require_*` обеспечивает условие или выдаёт ошибку. Избегай неоднозначного `check_*`.
- **Python:** модули, функции и переменные — `snake_case`, классы — `PascalCase`, константы — `UPPER_SNAKE_CASE`.
- **React/TS:** компоненты, интерфейсы и типы — `PascalCase`; функции/переменные — `camelCase`; хуки — `useFeature` (`useApplications`); локальные обработчики — `handleSubmit`, публичные callback-props — `onSubmit`; булевы переменные — `isLoading`, `hasAccess`, `canEdit`.
- Файлы React-компонентов — `PascalCase.tsx`; утилиты и API-файлы — последовательный `camelCase.ts` в пределах модуля; при наличии сложившегося локального соглашения соблюдай его.
- Имена тестов описывают **поведение и условие**, например `test_get_application_rejects_other_student` или `it("rejects access to another student's application", ...)`. Файлы: `test_*.py` и `*.test.ts(x)`.
- Таблицы и поля сохраняй по `docs/DB.md`, пути API — по принятым контрактам. Не переименовывай существующее ради косметического единообразия. Избегай неясных сокращений (`usr`, `appData2`), если нет принятого доменного смысла.
- Настройки Ruff/ESLint/Prettier и локальный стиль существующего кода имеют приоритет для **форматирования**; изменение смысловых соглашений и публичных имён требует согласования.

## Git: коммиты и ветки

- Сообщения коммитов: **Conventional Commits**, `type(scope): imperative action [TASK-XXX]`, например `feat(auth): implement login [TASK-012]`. Если работа не привязана к задаче, суффикс `[TASK-XXX]` опускается.
- Типы: `feat`, `fix`, `refactor`, `test`, `docs`, `chore`, `perf`, `ci`. `scope` — предметная область (`auth`, `schedule`, `academics`, `applications`, `notifications`, `news`) или инфраструктурная область (`db`, `ui`, `deploy`, `docs`); используй один вариант последовательно.
- Заголовок коммита — краткий, на английском, с глаголом в повелительном наклонении; один логически законченный смысл на коммит. Например: `fix(schedule): show moved lessons correctly [TASK-024]`.
- Ветки, **когда их создание разрешено**: `type/TASK-XXX-short-description`, например `feat/TASK-012-auth-login`, `fix/TASK-024-schedule-order`; короткое описание в `kebab-case`.
- Не выполняй commit, создание ветки, push, merge или PR без отдельного разрешения. Это соглашения о **названиях**, а не разрешение на Git-операции.

## Pull requests

Создавай PR и изменяй его метаданные только по отдельному разрешению пользователя. Если целевая ветка не указана, используй `main`; не выполняй merge без прямого поручения.

### Заголовок

- **Всегда на английском языке.**
- При наличии связанного issue используй формат `TASK-XXX — Issue name without number`: идентификатор задачи и содержательное название issue без повторения номера. Если название issue на русском, переведи его на английский без изменения смысла.
- Если issue нет, используй произвольный краткий английский заголовок, отражающий суть изменений.

### Описание

Описание PR всегда пиши **на русском языке**. Оно должно быть кратким, проверяемым и соответствовать фактическому diff. Используй разделы:

1. **Резюме** — цель, результат, ссылка на issue (только если PR связан с issue: `Closes #N` при полном выполнении задачи, иначе `Refs #N`) и связанные `REQ-*`, если применимо.
2. **Основные изменения** — существенные изменения и их назначение, без копирования всего issue.
3. **Проверки** — реально запущенные команды, результаты, важные сценарии и то, что не удалось проверить. Не заявляй об успешных проверках без запуска.
4. **Ограничения и дальнейшие действия** — известные ограничения, оставшаяся работа, необходимые ручные настройки (включая production) и несогласованные вопросы. Если ничего нет, кратко укажи это.
5. **Исправления по итогам ревью** — добавляй, только если они были. В **одном блоке** кратко перечисли замечания по идентификаторам (`F-01`, `SEC-01` и т. п.) и что именно исправлено; неустранённые или частично исправленные пункты обозначь явно.

Обновляй описание PR после существенных исправлений. Для документационных правок указывай проверку согласованности, а не выдуманные результаты несвязанных тестов. Отчёт агента в чате и описание PR — разные результаты; создание PR не означает приёмку задачи.

## Выполнение `TASK-XXX`

Рабочие спецификации задают основу реализации; пункты `TBD` остаются неутверждёнными. Статус `Draft` у issue не означает разрешение на разработку. Прямое поручение пользователя реализовать конкретную задачу разрешает её выполнение в указанном объёме, но не утверждает остальные задачи и не означает приёмку результата.

1. Найди описание задачи. Если его нет, **не придумывай содержимое по номеру**.
2. Проверь связанные `REQ-*`, зависимости, критерии приёмки и существующую реализацию.
3. Для нетривиальной задачи кратко определи порядок изменений; при конфликте с документами обозначь его до реализации.
4. Реализуй минимальное законченное решение, соблюдая принятые контракты и соглашения проекта.
5. Добавь или обнови необходимые тесты. Используй реальные команды из репозитория; не выдумывай их.
6. Запусти доступные проверки, проверь итоговый diff и сообщи о результате.

После существенных изменений проекта проверяй актуальность `README.md` и обновляй его при необходимости, особенно если изменились реализованные возможности, конфигурация, зависимости, команды запуска или проверки.

## Проверки и ограничения

- Тестируй не только успешные сценарии, но и ошибки, границы доступа и сохранение данных там, где это применимо.
- Для изменений БД используй миграции и проверки, соответствующие PostgreSQL; не считай SQLite эквивалентом для конкурентных сценариев.
- Для затронутых экранов учитывай мобильную ширину **360 px**, состояния загрузки, пустого результата и ошибки.
- Не трогай чужие незакоммиченные изменения. Без прямого разрешения **не выполняй** commit, push, merge, force-push, `git reset --hard`, разрушительные миграции и деплой.
- Если окружение или проверка недоступны, честно укажи это. Не утверждай, что тесты прошли, если их не запускал.

## Завершение задачи

Кратко отчитайся **на русском**:

- **Задача:** ID, статус и связанные `REQ-*`.
- **Изменения:** что сделано и какие файлы затронуты.
- **Проверки:** что запускалось, что прошло и что не удалось проверить.
- **Ограничения:** риски, открытые вопросы и оставшаяся работа.

Задача готова к приёмке, когда выполнены её критерии, соблюдены связанные спецификации, проведены доступные проверки и не внесены посторонние изменения. **Окончательно принимает работу пользователь.**
