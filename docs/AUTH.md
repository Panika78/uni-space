## Конфигурация

`JWT_SIGNING_KEY` обязателен во всех окружениях; встроенного ключа нет.
Минимум 32 байта и 16 различных символов; production дополнительно запрещает
полные повторы многосимвольных блоков, известные последовательности и
маркеры тестовых/примерных ключей. Эти простые правила не доказывают энтропию
и не заменяют генератор случайных чисел: используйте
приватный случайный ключ и хранилище секретов. Генерация:
`python -c 'import secrets; print(secrets.token_urlsafe(48))'`.
Значение из `.env.example` предназначено только для разработки.
Ошибки запуска сообщают имена некорректных настроек без значений.

| Переменная | Значение / ограничения |
|---|---|
| `APP_ENV` | `development` по умолчанию; `test` для изолированных проверок; `production` включает строгую валидацию |
| `JWT_SIGNING_KEY` | Обязательный секрет |
| `JWT_ISSUER` | `uni-space`, непустая строка без крайних пробелов |
| `JWT_AUDIENCE` | `uni-space-api`, непустая строка без крайних пробелов |
| `ACCESS_TTL_SECONDS` | 600, диапазон 1–3600 |
| `SESSION_TTL_SECONDS` | 604800, диапазон 1–2592000; абсолютный срок |
| `COOKIE_SECURE` | `true` по умолчанию; `false` только вне production |
| `ALLOWED_ORIGINS` | JSON-массив точных origins, например `["https://uni.example"]` |
| `PROXY_HEADERS_ENABLED` | `false` по умолчанию; `true` только вместе с непустым доверенным списком |
| `TRUSTED_PROXY_IPS` | `[]` по умолчанию; JSON-массив фактических IP/CIDR доверенных proxy |

Production требует `COOKIE_SECURE=true` и только HTTPS origins. Для локального
HTTP явно задайте `COOKIE_SECURE=false` и `ALLOWED_ORIGINS=["http://localhost:5173"]`.
Origins проверяются целиком как сериализованные HTTP/HTTPS origins: без пути,
userinfo, пробелов, query/fragment (включая пустые `?`/`#`) и пустого порта.
Допустимы localhost, DNS/IDNA-имена в ASCII, IPv4, IPv6 в квадратных скобках
и числовые порты 1–65535. Значения не нормализуются; точное сравнение сохранено.
SPA и API размещаются на одном origin; CORS для внешних сайтов не добавлен.

`compose.yaml` предназначен для локальной разработки, не является готовой
production-инфраструктурой: он не настраивает TLS, reverse proxy и управление
секретами. По умолчанию `APP_ENV=development`; явно заданный `APP_ENV=production`
передаётся приложению и включает все production-проверки без подмены режима.
Локальный API публикуется только на `127.0.0.1:8000`. Установка production-режима
сама по себе не делает локальный Compose пригодным для публичного размещения.
Тестовый conftest, CI и экспорт OpenAPI используют публичные фиктивные ключи;
это не резервные ключи работающего API. Для отдельных команд миграций на
изолированной тестовой БД:

```bash
export APP_ENV=test
export JWT_SIGNING_KEY=test-only-0123456789-ABCDEFGHIJKLMNOPQRSTUVWXYZ
export DATABASE_URL=postgresql+psycopg://uni_space_test:test-only-password@127.0.0.1:55432/uni_space_test
```

### Режим запуска production (SEC-03)

Для будущего публичного развёртывания используйте явную команду launcher:

```bash
python -m app.core.server --production
```

При запуске через uv перед ней остаётся обычный префикс
`uv run --locked --python 3.12.16`. Контейнерный entrypoint также допускает эту
команду вместо локального CMD; адрес/порт выбираются под фактическую внутреннюю
сеть reverse proxy. Это команда запуска API, **не готовый production-деплой**.

**Гарантии кода:** Settings всегда проверяет обязательный JWT-ключ, формат Origins
и политику доверенных proxy. При APP_ENV=production дополнительно отклоняет
известные демонстрационные/тестовые/предсказуемые ключи, COOKIE_SECURE=false и
не-HTTPS Origins. Эти валидаторы существовали до SEC-03; они не доказывают
случайность ключа, работоспособность TLS или корректность сети.

**Гарантия команды запуска:** `--production` устанавливает APP_ENV=production
до load_settings и передаёт этот режим дочернему Uvicorn через окружение.
Перед установкой режима удаляются регистронезависимые варианты имени APP_ENV,
которые Settings иначе мог бы прочитать как конфликтующие настройки. Унаследованные
APP_ENV=development/test, app_env и скопированный development `.env` не могут
понизить режим этой команды. Небезопасные настройки завершают процесс до запуска
Uvicorn; значения секретов в диагностике не выводятся. Флаг не включает доверие
к proxy и не меняет его allowlist. Без флага прежний выбор APP_ENV сохранён,
включая удобный локальный development-запуск.

**Обязательные действия оператора:** закрепить эту команду и APP_ENV=production
в deployment/service definition (в production Compose уже закреплены); использовать отдельные приватные секреты
(не копировать `.env.example`), COOKIE_SECURE=true и точные HTTPS Origins своего
сайта. До публикации настроить TLS, reverse proxy, закрытый доступ к API/БД и
проверить фактический клиентский IP/лимиты по [разделу о proxy](#ограничение-login).
В CI/deployment проверять итоговую команду/окружение и отказ при небезопасных
настройках; применение production-флага должно проверяться на целевой платформе.

**Статус SEC-03:** TASK-019 закрепляет launcher и APP_ENV=production в отдельном
`compose.prod.yaml`; реальный локальный прогон проверяет отказ небезопасного
запуска, TLS и proxy. Инструкция — [PRODUCTION.md](PRODUCTION.md).
Фактическое публичное развёртывание и его проверки остаются в TASK-020.
Launcher защищает только выбранную production-команду; он не распознаёт публикацию
локального Compose через внешний proxy/туннель и не запрещает запуск другим
entrypoint или без флага. HTTP-заголовки/IP для определения публичности не
используются. Режим запуска, TLS, секреты и реальное развёртывание
**нужно проверить на целевом хосте в TASK-020**. Не публикуйте локальную
конфигурацию без этих действий; документация сама по себе не обеспечивает защиту.

## Запросы и защита

- Login принимает строгие строки `login` (1–256) и `password` (1–1024 символов),
  без обрезки пробелов. Неизвестные поля запрещены. Проверяется именно Argon2id;
  для неизвестного логина выполняется проверка фиктивного Argon2id-хеша.
  Неверный пароль, неизвестный логин и неактивный аккаунт дают одинаковый
  `401 invalid_credentials`.
- Refresh/logout принимают refresh только через cookie; logout дополнительно допускает необязательный access Bearer при неизвестной/отсутствующей cookie. Тела не принимаются:
  непустое тело в пределах лимита даёт `422 validation_error`.
- Все три auth-маршрута ограничены **16384 байтами (16 КиБ)** до чтения/разбора тела
  FastAPI и запуска зависимостей. Этого достаточно для максимальных login/password
  даже при JSON-экранировании каждого символа, включая суррогатные пары Unicode
  за пределами BMP (до 12 байт на символ). Считаются фактические ASGI-байты,
  независимо от `Content-Length`, в том числе без него и при chunked-передаче.
  Превышение даёт `413 request_too_large` в едином формате API; переполнивший
  чанк не добавляется в буфер, оставшаяся часть потока не дочитывается.
  Пустые тела и остальные ошибки auth обрабатываются как раньше.
- Все три маршрута требуют ровно один `Origin`, точно совпадающий с разрешённым.
  Отсутствующий, повторный, `null` и запрещённый заголовок дают
  `403 origin_not_allowed`, включая logout. CLI также передаёт Origin.
- Cookie `__Host-uni_space_refresh`: `HttpOnly`, `SameSite=Lax`, `Path=/`,
  без `Domain`, `Secure` обязательно. Префикс `__Host-` обеспечивает host-only
  область и требует HTTPS в браузере. `Expires` и округлённый вниз `Max-Age`
  не превышают абсолютный срок сессии. Удаление использует те же атрибуты.
  Origin и SameSite защищают cookie-маршруты от CSRF.
- Старое имя `uni_space_refresh` больше не принимается. Login и logout посылают
  очистку legacy host-only cookie с прежним `Path=/api/v1/auth`; cookie с
  parent-domain scope не может быть очищена без знания домена и игнорируется.
  Пользователь проходит login заново; существующие старые сессии истекают по
  исходному TTL. В development/test с `COOKIE_SECURE=false` используется
  отдельное имя `uni_space_refresh_dev` с прежним ограниченным Path для работы
  локального HTTP; такой режим не предназначен для публикации.
- Access использует только HS256, обязательные типизированные claims,
  стандартные проверки PyJWT и явные проверки значений. `sub`/`sid` — строки
  положительных BIGINT; claims роли не предоставляют права.
- `get_current_user` на каждом запросе проверяет в PostgreSQL пользователя,
  владельца сессии, активность, отзыв и срок. `get_current_student` требует
  актуальную роль `student` и собственный профиль, без клиентского `student_id`.
- Существующие middleware/обработчики дают `no-store`, `X-Request-ID` и единый
  формат ошибок без исходных значений и внутренних исключений.

## Транзакции

Login сначала читает ID, хеш и активность обычным SELECT и проверяет Argon2id
(фиктивный хеш для неизвестного логина), не удерживая row lock во время проверки.
Неверный пароль и неактивный аккаунт отклоняются без блокировки пользователя.
После успешной проверки login берёт `FOR UPDATE` по тому же ID/логину,
перечитывает актуальное состояние и требует активность и неизменность проверенного
хеша. При смене хеша вход отклоняется, даже если новый хеш соответствует тому же
паролю: нужна новая попытка. Дорогая повторная проверка под lock не выполняется.
Пользовательская блокировка удерживается до атомарного commit сессии и первого
refresh, сохраняя сериализацию с конкурентными изменениями пользователя. Refresh содержит 256 случайных бит;
в БД сохраняется только SHA-256. Срок сессии не продлевается.

При успешном login сервер сначала ищет сессию по текущей refresh-cookie и отзывает
только её с причиной `login_replaced`, затем создаёт новую. Это позволяет обычному
повторному входу заменить cookie-сессию после неопределённого результата refresh или
logout. Проверка credentials завершается до отзыва: неверный пароль не отзывает
прежнюю сессию; независимые сессии на других устройствах не затрагиваются.

Refresh/logout находят ID сессии по хешу, затем блокируют строку сессии через
`FOR UPDATE`. При стандартной PostgreSQL `READ COMMITTED` после ожидания
повторно читается актуальное состояние (`populate_existing=True`), время
проверяется после блокировки. Проверяется также принадлежность родителя и
сроки токена/сессии. Старый токен обновляется с flush до вставки продолжения,
соблюдая существующие уникальные ограничения TASK-005.

Reuse отзывает только найденную сессию и все её refresh. Commit выполняется
до HTTP-ошибки, поэтому закрытие dependency не откатывает отзыв. Logout
использует ту же блокировку; известная cookie имеет приоритет, включая использованные
и уже отозванные токены. При её отсутствии/неизвестности валидный access проверяется
существующим validate_access_token (подпись, HS256, обязательные типизированные
claims, issuer/audience, сроки, token_type). Сессия выбирается по sid И user_id=sub
с FOR UPDATE/populate_existing; revoke_session фиксирует отзыв/историю refresh
в той же транзакции. User row lock не добавляется. При конфликте cookie/Bearer
отзывается только cookie-сессия. Невалидный/истёкший JWT, неизвестный sid и чужой
владелец игнорируются; без пригодных идентификаторов logout возвращает
`session_revoked=false` и удаляет cookie. Уже отозванная сессия не меняет исходное время/причину отзыва. Токены
выдаются после commit. Блокировка пользователя после блокировки сессии не
захватывается; порядок совместим с будущими операциями MVP 2.

Для соединений API на уровне PostgreSQL установлены `lock_timeout=5000ms` и
`statement_timeout=30000ms`. Пять секунд оставляют место штатной сериализации
refresh/logout по блокировке сессии, а общий предел завершает слишком долгий SQL.
Таймаут не повторяет запрос автоматически: ошибка проходит через общий безопасный
ответ `internal_error`; зависимость откатывает незавершённую транзакцию и закрывает
сессию до возврата соединения в пул. Поэтому таймаут во время refresh откатывает
операцию целиком, не меняя состояние refresh-цепочки. Уже commit-нутый reuse revoke
по-прежнему остаётся зафиксированным до HTTP-ошибки. Таймаут может сделать
результат запроса неизвестным клиенту, поэтому refresh-клиент не должен
автоматически повторять запрос.

## Ограничение login

**5 попыток за фиксированное окно 60 секунд на IP в `request.client`, определённый
Uvicorn**. При выключенной обработке forwarded-заголовков это IP соединения;
при включённой — IP по явно настроенной политике доверенных proxy.
Окно начинается с первой попытки. Учитываются успешные/неуспешные запросы,
включая ошибки тела в пределах 16 КиБ, после проверки Origin.
Превышение размера отклоняется раньше разбора JSON, Origin и rate limiter.
Успешный вход счётчик не сбрасывает.
При исчерпании — `429 rate_limited`; `Retry-After` — округлённый вверх остаток
окна в секундах, минимум 1. Доступ к состоянию защищён lock. На каждой попытке
удаляются все истёкшие окна; без новых попыток записи остаются до следующего
запроса или завершения процесса.

Приложение не разбирает `X-Forwarded-For` самостоятельно. Запускайте сервер через
`uv run --locked --python 3.12.16 python -m app.core.server` (для разработки
допустим `--reload`). Docker использует тот же launcher. Он читает существующий
Settings и передаёт Uvicorn явные параметры:

- По умолчанию — `--no-proxy-headers`, независимо от внешних Uvicorn env defaults.
- Только с `PROXY_HEADERS_ENABLED=true` и непустым `TRUSTED_PROXY_IPS` —
  `--proxy-headers --forwarded-allow-ips <проверенный список>`.
- Разрешены точные IPv4/IPv6 и канонические CIDR. Hostname, пустой элемент,
  некорректная сеть, `*`, сети `/0` и совокупности сетей, покрывающие все адреса
  одного семейства, запрещены. В production список дополнительно ограничен
  отдельными адресами RFC1918, IPv6 ULA и loopback; эквивалентные `/32` и `/128`
  разрешены, многоадресные CIDR запрещены. Development/test сохраняют поддержку CIDR.
  При заданном `PUBLIC_ORIGIN` production Settings требуют один совпадающий
  канонический HTTPS-origin в `ALLOWED_ORIGINS`; Compose выводит его автоматически.
  Отдельный запуск API без `PUBLIC_ORIGIN` сохраняет существующую настройку origins.
  Список без включённого флага и флаг без списка
  также приводят к отказу запуска; небезопасного fallback нет.
- `APP_ENV=production` не включает доверие к proxy автоматически. По умолчанию
  оно выключено и в production. После изменения списка/флага нужен рестарт.

**Поддержка доверенного proxy не завершает настройку production-развёртывания
и не означает автоматической защиты публичного сервиса.** В production Compose
назначен точный внутренний IP Nginx (`NGINX_PROXY_IP`); проверьте отсутствие
конфликтов подсетей на целевом хосте. При публичном развёртывании обязательно:

1. Настроить реальный reverse proxy и достоверную передачу клиентского IP:
   proxy должен удалять/перезаписывать недостоверные forwarded-заголовки либо
   формировать безопасную цепочку с фактическим адресом соединения.
2. Указать фактические IP/сети proxy в `TRUSTED_PROXY_IPS`, явно включить флаг;
   не доверять адресам произвольных клиентов или публичным широким сетям.
3. Закрыть прямой доступ к backend в обход proxy сетевыми правилами/изоляцией.
   Сам allowlist Uvicorn не заменяет эту защиту.
4. На реальной инфраструктуре проверить определяемые IP, независимость лимитов
   разных клиентов, блокировку шестой попытки только соответствующего клиента
   и невозможность подмены IP через заголовки или обход proxy.

Без настроенного доверенного proxy лимит применяется к адресу соединения;
за общим proxy его клиенты разделяют счётчик. Доверие и сетевую изоляцию
необходимо настроить до публичного размещения. В тестах проверены настоящий
Uvicorn и HTTP-запросы от доверенного/недоверенного peer с forwarded-заголовками,
включая IPv6 и цепочку адресов. TASK-019 добавляет реальный Nginx/TLS
и проверки нескольких Docker peer в `deploy/test_production.py`; публичное
окружение не разворачивалось и не проверялось.

## Известные ограничения

- Лимит тела ограничивает прикладной буфер auth-запроса; размер отдельного ASGI-чанка,
  сетевые буферы, время передачи и число соединений задаются сервером/proxy.
  Ограничения времени и соединений при публичном размещении настраиваются отдельно.
- Rate limiter хранится в памяти одного процесса: рестарт сбрасывает окна,
  workers/реплики имеют независимые лимиты. Для общего лимита нужен один процесс
  либо отдельно согласованный общий механизм/proxy. Пользователи за NAT делят
  лимит; распределённые IP могут обходить его.
- Строгий reuse не имеет окна повторного принятия. Гонка вкладок или потеря
  успешного ответа refresh может требовать нового входа. Координация вкладок,
  восстановление после reload и браузерный жизненный цикл реализованы в TASK-007
  и описаны ниже.
- Старые refresh сохраняются для обнаружения reuse. Автоочистка истории не
  добавлена: срок хранения остаётся TBD в DB.md и требует отдельной политики.
- Уже выполняющиеся запросы не прерываются задним числом. Проверка активности
  блокирует новые запросы; административная блокировка/разблокировка с отзывом

- TASK-009 реализует `GET /users/me`: только текущий студент, академические

## Проверки

Используются обычные команды проекта: `uv run --locked --python 3.12.16 pytest
-m "not integration"` и `uv run --locked --python 3.12.16 pytest -m integration`.
Интеграционные тесты требуют изолированную PostgreSQL из `compose.test.yaml`,
проверяют имя БД/роли, применяют миграции и очищают собственные вымышленные данные.

HTTPX проверяет auth-маршруты, зависимости, отзыв после ошибки, изоляцию сессий,
cookie, Origin и лимит. Конкурентные HTTPX-запросы используют разные PostgreSQL
соединения и реальные транзакции с commit-видимыми данными. Первый запрос
удерживает lock, монитор проверяет `pg_blocking_pids` второго соединения.
Оба намеренно сохраняют устаревшие ORM-объекты: проверяется повторное чтение
для refresh/refresh и обоих порядков refresh/logout.

Регрессии конфигурации в модульном наборе требуют CLI Docker Compose:
`docker compose config --format json` проверяет итоговое окружение и loopback-порт,
а отдельный Python-процесс через существующий entrypoint импортирует приложение
в development/production, включая отказ на небезопасных настройках. Для этих
тестов демон Docker и соединение с PostgreSQL не требуются. Отдельные регрессии
launcher проверяют --production при унаследованном development/test и локальном
.env, отказ на небезопасных ключах/cookie/Origins/proxy и настоящий Uvicorn по HTTP
с прежней политикой доверия. Эти локальные проверки не заменяют реальный TLS/proxy
и deployment manifest. Тесты ограничения
тела используют HTTPX на настоящих auth-маршрутах, проверяют chunked-потоки без
Content-Length, ложную длину, ранний отказ и отсутствие разбора oversized JSON.

Защита login от удержания row lock (SEC-03 из PR #27) проверяется HTTPX
с независимыми PostgreSQL-соединениями: неверные login
завершаются при удерживаемой внешней row lock; при двух синхронизированных проверках
Argon2id третья транзакция получает `FOR UPDATE NOWAIT`. Argon2id в этих тестах
реальный, обёртка используется только для синхронизации. Отдельно проверяется
ожидание корректного login через `pg_blocking_pids` и отказ после commit
деактивации/изменения хеша. Это доказательства внутреннего механизма с
искусственными блокировками, а не измерение надёжности удалённой timing-эксплуатации
и не гарантия отсутствия всех возможных побочных каналов. Атомарность успешного
login и rollback при ошибке первого refresh покрываются существующими тестами.

## Браузерный жизненный цикл (TASK-007)

`features/auth/AuthSession` хранит access только в памяти. `AuthProvider`
подключён к существующему QueryClient; маршруты различают `initializing`,
`authenticated`, `unauthenticated`. До завершения начального refresh кабинет
не отображается. `/login` после входа открывает временный `/schedule`; профиль,
содержимое расписания и их API относятся к TASK-009/010. Регистрация,
восстановление пароля, быстрое переключение аккаунтов и финальный дизайн не входят
в TASK-007.

Все запросы проходят через `shared/api/apiFetch`. Для защищённого запроса нужно
передать `{ authenticated: true, signal }`: клиент добавляет Bearer, объединяет
сигнал вызывающего кода с сигналом поколения авторизации, проверяет поколение
после ответа и допускает ровно один повтор после `401 access_expired` и успешного
refresh. Внутри вкладки используется общая Promise refresh. `invalid_access`
и `session_invalid` завершают локальную авторизацию без refresh. Начальные
`invalid_refresh`, `invalid_access`, `session_invalid` означают отсутствие входа,
без сетевого предупреждения. `403`, бизнес-ошибки, сеть и отмена не запускают refresh.
Повторы Query/mutation отключены; также отключены retryOnMount, refetch при focus
и reconnect. При будущих задачах нельзя переопределять эти настройки так, чтобы
обходить политику API. Потоковые тела повторно не используйте; обычные JSON-тела
и клонируемый `Request` поддержаны.

Для `authenticated: true` адрес разрешается через URL относительно текущего
адреса страницы: только HTTP(S), точный origin приложения и нормализованный путь
с префиксом `/api/v1/` (включая завершающий `/`). Проверка выполняется до доступа
к access и отправки Fetch, а также перед повтором. Относительные строки и URL
фиксируются в абсолютный нормализованный адрес, URL объекта Request неизменяем.
Недопустимые адреса дают локальный `invalid_api_target` без URL/токена в сообщении.
Encoded-разделители `%2f`/`%5c` и userinfo отклоняются, чтобы исключить неоднозначную
интерпретацию пути proxy. `/api/v10/` и traversal за пределы API не разрешены.
Обычные запросы без authenticated сохраняют прежнее поведение.

Authenticated-запросы используют `redirect: 'error'`, включая повтор: они не
следуют никаким перенаправлениям. Fetch снимает Authorization при смене origin,
но сохраняет его при redirect внутри origin за пределы `/api/v1/`; поэтому одной
браузерной защиты недостаточно для ограничения API-префиксом. Серверный API
не требует redirect; если он понадобится, контракт следует согласовать отдельно.

### Координация вкладок

Одна эксклюзивная Web Lock `uni-space.auth` сериализует login, refresh и logout
для одного origin и раздела хранилища браузера. Каждый refresh использует cookie,
актуальную именно при отправке Fetch: вкладки последовательно вращают общую
cookie, получая собственные access без передачи токенов между вкладками.
Блокировки с TTL в localStorage и принудительный захват не используются:
приостановленная вкладка может ещё выполнять запрос, поэтому истечение аренды
не доказывает безопасность нового refresh.

В localStorage находятся только несекретные служебные ключи:

- `uni-space.auth-epoch`: случайный идентификатор намерения сменить авторизацию;
- `uni-space.auth-state`: поколение операции, `blocked`, `pending`, необязательный
  `ended` после подтверждённого отсутствия пригодной сессии или подтверждённого logout (`session_revoked=true`);
- кратковременный `uni-space.storage-probe` проверяет доступность записи отдельно
  от журнала операции.

Поколение намерения записывается немедленно перед login/logout, а журнал операции
пишется только владельцем lock. Разделение не позволяет позднему refresh
перезаписать новое намерение или инициализации другой вкладки стереть `pending`.
Несовпадение поколений блокирует восстановление. `storage`, `pageshow`, `focus`
сбрасывают прежний вход; перед запросом и применением ответа поколение также
перечитывается синхронно. Смена поколения отменяет запросы и очищает QueryClient,
включая кеш mutations. Другая вкладка после нового login остаётся без старых
данных; для восстановления нового входа нужно обновить страницу либо войти явно.

Перед отправкой refresh записывается `pending=true`. Только подтверждённый успех
снимает его; неопределённый результат, включая 15-секундный таймаут активного
запроса, запрещает дальнейший refresh. При закрытии вкладки Web Locks освобождает
lock, но журнал остаётся. Если процесс исчез между записью маркера и отправкой
запроса, возможен консервативный повторный вход. Это предпочтительнее повторного
предъявления потенциально использованной cookie. Login, refresh и logout после
сетевой ошибки автоматически не повторяются.

Logout немедленно скрывает данные во всех активных вкладках, а серверный запрос
ждёт завершения предыдущей cookie-операции под той же lock. До beginChange access
копируется только в локальную переменную; Authorization отправляется через общий
apiFetch без authenticated:true только на фиксированный `/api/v1/auth/logout`,
с redirect:error. Поколение проверяется до beginChange и под lock; сменившийся
журнал не позволяет позднему logout старого поколения отозвать новую cookie-сессию.
Ответ logout удаляет cookie и содержит `session_revoked`: `true`, когда конкретная
сессия идентифицирована и отозвана (или уже была отозвана), иначе `false`. Если cookie
не идентифицирует сессию, а Bearer отсутствует/истёк/невалиден, backend не знает,
какую сессию отзывать. UI подтверждает выход только при `session_revoked=true`.
При неподтверждённом выходе UI немедленно скрывает приватные данные, отменяет
запросы, очищает кеш и показывает обычную форму входа с понятным сообщением.
Журнал сохраняет `blocked=true`, чтобы reload не восстановил потенциально
неотозванную сессию. Событие `online`, reload и смена вкладки не отправляют
новый logout или refresh. Пользователь может явно войти снова: успешный login
заменяет сессию текущей cookie после проверки credentials; неверный пароль её не
отзывает. Сессии других устройств не затрагиваются.

Если журнал повреждён до начала logout, frontend закрывает приватный UI и не
отправляет запрос с неизвестной cookie. При таймауте ожидания Web Lock запрос
также не отправляется и не запускается позднее после освобождения lock.
В обоих случаях показывается сообщение о неподтверждённом выходе без обещания
автоматического повтора. Если Web Locks или localStorage недоступны, показывается
сообщение о несовместимости браузера. Если cookie отсутствует, а access уже утрачен,
API возвращает `session_revoked=false`; серверная сессия может жить до абсолютного
срока. Выход со всех устройств не выполняется.

Если сервер создал сессию, но ответ потерян до
получения браузером cookie, клиент не имеет её идентификатора: такая недоступная
сессия может оставаться в БД до абсолютного срока. Полное устранение этого узкого
случая потребует отдельного серверного механизма идентификации попытки login либо
отзыва всех сессий аккаунта; последний вариант затронул бы другие устройства.
Reload не восстанавливает неопределённую refresh-сессию и показывает обычную форму входа.
После `session_revoked=true` журнал сохраняет `blocked=true`, `pending=false`,
`ended=true`: reload показывает обычную форму входа без предупреждения и без
HTTP refresh. `synchronize()` во второй вкладке синхронизирует локальное состояние
после получения результата обработки, даже если поколение уже было сброшено в начале
logout. Признак `ended` относится только к совпадающему
поколению при отсутствии `pending`; старый журнал не подтверждает новый logout.
В контексте logout ended фиксирует завершённое локальное состояние и запрет
автовосстановления, а не доказательство отсутствия/отзыва всех серверных сессий.
Если все пригодные идентификаторы утрачены, неидентифицированная серверная сессия
может оставаться до своего абсолютного срока; выход со всех устройств не добавлен.

После `401 invalid_credentials` login сохраняет `ended=true` для нового
поколения только если отсутствие пригодной сессии/завершение локального logout
было зафиксировано до попытки, а журнал
этого предшествующего поколения всё ещё содержит `ended=true` без pending при
получении Web Lock. Проверка и запись выполняются под lock, а поздний ответ
проверяет актуальное поколение до изменения журнала. Reload в таком случае
показывает обычный login без предупреждения и без refresh/повтора login.
Если ранее могла существовать сессия другого аккаунта, результат неизвестен,
либо журнал уже относится к другому поколению, восстановление остаётся запрещено.
В частности, таймаут, сеть и HTTP 5xx не возвращают ended, даже если отсутствие
сессии было известно до отправки login.

При timeout, сетевом сбое, некорректном ответе, HTTP 5xx или ошибке координации
потенциально затронутая сессия остаётся заблокированной для автоматического refresh,
а приватные данные очищены. Интерфейс показывает обычную форму входа и только
понятное краткое сообщение; внутренние причины, cookie и состояние журнала не
раскрываются. Следующий login отправляется только после обычного действия пользователя,
не автоматически. При успешной проверке credentials сервер отзывает сессию,
идентифицированную текущей cookie, и выдаёт новую.

### Браузеры и ограничения

Нужны HTTPS (либо localhost), Web Locks, доступный localStorage, `crypto.randomUUID`,
`AbortSignal.any` и `AbortSignal.timeout`. Целевая совместимость: Chromium 116+,
Firefox 124+, Safari 17.4+; фактически браузерный прогон выполнен в Chromium 156,
Firefox/Safari пока не проверены. При недоступной координации cookie-операции
не выполняются; пользователь видит обычную форму входа и понятное сообщение о
несовместимости браузера/недоступном хранилище сайта.
Полифилы и небезопасный fallback не добавлены.

Координация действует только для сотрудничающих вкладок одного origin/раздела
хранилища. Другие клиенты, старые версии приложения, ручное удаление служебных
ключей при сохранённой cookie и вмешательство расширений вне этой гарантии.
Серверный строгий reuse остаётся последней защитой. Не очищайте только служебные
ключи ради обхода блокировки: используйте обычную форму входа.
Замороженная вкладка обрабатывает события после возобновления; `pageshow`/focus и
проверка поколения защищают дальнейшие запросы. Приостановленный владелец lock
может задержать другие вкладки до возобновления/закрытия; lock не отбирается. Для ожидания получения lock установлен отдельный
10-секундный таймер в ожидающей вкладке. По истечении deadline AbortController отменяет только её
ожидающий `navigator.locks.request` через штатную опцию signal; callback и HTTP
не запускаются, в том числе после последующего освобождения lock. UI выходит из
busy/initializing и оставляет обычную форму входа; технические причины не выводятся.
Приватные данные очищаются; logout автоматически не повторяется.

Таймер ожидания снимается при получении lock. Получившая её операция сохраняет
отдельный 15-секундный HTTP-таймаут и исходную семантику неопределённого результата;
ожидание не прерывает уже выполняющийся запрос и не даёт права на новый refresh.
Отменённый waiter не меняет чужой журнал pending/blocked/ended. Для login/logout
сохраняется записанное до ожидания новое намерение auth-epoch: несовпадение журнала
после reload запрещает молчаливое восстановление. У начального refresh, не
предъявлявшего cookie, журнал не изменяется; пользовательский reload может начать
новую проверку. Подтверждённый ended текущего поколения позволяет сразу показать
обычный login без ожидания lock. Автоматических повторов после deadline нет.
Таймаут браузера может приостанавливаться вместе с документом. Нельзя обещать
немедленное обновление содержимого замороженного документа.

### Origin и локальный запуск

Используйте `http://localhost:5173`, `COOKIE_SECURE=false` и
`ALLOWED_ORIGINS='["http://localhost:5173"]'` из `.env.example`. Vite proxy
меняет Host через `changeOrigin`, сохраняя Origin браузера. JavaScript не задаёт
Origin вручную. Если открыть другой порт или `127.0.0.1` вместо localhost,
нужно явно добавить точный origin в локальную конфигурацию сервера. Серверная
проверка Origin и ограничения cookie не ослаблены.

### Воспроизводимые браузерные проверки

`frontend/e2e/auth.browser.mjs` запускается с Vite и настоящим backend, отдельной
тестовой PostgreSQL и двумя заранее подготовленными вымышленными аккаунтами.
Передайте `AUTH_TEST_LOGIN_A`, `AUTH_TEST_LOGIN_B`, `AUTH_TEST_PASSWORD` через
окружение; реальные учётные данные использовать нельзя. Скрипт делает шесть реальных
login-попыток (управляемые ошибки не отправляются в backend). При `429` он проверяет
отсутствие автоматического login и явно повторяет ввод после указанного
`Retry-After`. Перед повторным полным прогоном дождитесь нового окна серверного
limiter. При необходимости `AUTH_TEST_URL` меняет адрес приложения,
`CHROMIUM_PATH` — путь Chromium. Playwright должен быть доступен в окружении;
`PLAYWRIGHT_MODULE` может указать абсолютный путь к его `index.mjs` без изменения
зависимостей приложения:

Для прогона запустите Vite с тестовым proxy (порт 18080 должен быть свободен):

```bash
cd frontend
API_PROXY_TARGET=http://127.0.0.1:18080 npm run dev
```

Затем из корня репозитория с указанными переменными окружения:

```bash
node frontend/e2e/auth.browser.mjs
```

Login/reload/logout и ротация выполняются настоящим backend. Дополнительный
тестовый защищённый API заменён только перехватом браузерных запросов;
`/users/me` обслуживается настоящим backend, кроме явно синтетического
login/Web Locks-блока с фиктивным токеном и соответствующим профилем; никакой тестовый
маршрут в production API не добавлен. Потеря ответов refresh/logout моделируется
после выполнения серверного запроса локальным fault proxy на `127.0.0.1:18080`
(backend по умолчанию `127.0.0.1:8000`, либо `AUTH_TEST_API_URL`). Proxy отправляет
операцию один раз и не доставляет ответ/Set-Cookie; при закрытии вкладки удерживает
ответ уже выполненной ротации. Он существует только на время теста. Проверяются две вкладки, закрытие владельца
lock, AbortController, отложенный ответ прежнего пользователя, мобильная ширина,
Retry-After и отсутствие токенов в persistent storage. Дополнительно реальный
Web Locks manager проверяет отмену очереди login/logout/начального refresh в двух
вкладках с удерживаемой lock, отсутствие позднего POST после её освобождения и
отсутствие автоматического logout после reload/события online и refresh. Управляемые
redirect проверяют, что authenticated Fetch не обращается к внешнему origin или
к пути за пределами API. Все тестовые адреса и токены вымышлены. Полный E2E с реальными
`/users/me`, истечением access на пользовательском API, персональными данными и
расписанием отложен до TASK-009/010; HTTP-политика и кеш сейчас проверяются
управляемыми ответами Vitest и браузера.

### Развёртывание исправления SEC-01

Новых переменных окружения, таблиц, миграций и зависимостей нет. Обновите backend
до или вместе с frontend: старый backend понимает только cookie и не реализует
Bearer fallback. Старые cookie-only клиенты совместимы с новым backend. OpenAPI
описывает Bearer как необязательный (security HTTPBearer или анонимный запрос);
ответ `200` содержит `session_revoked`; клиенты, которым требуется подтверждение,
должны учитывать это поле.


### Журналы production (SEC-03 из PR #31)

В production `app.core.server` добавляет явный `--no-access-log`: стандартный
access log Uvicorn включает query string и здесь не используется. Это не меняет
`uvicorn.error` и безопасные сообщения об ошибках API; доступы пишет Nginx без
query string. В development/test прежнее журналирование сохранено. Подробности,
границы гарантии и проверка вымышленного query-маркера — в
[PRODUCTION.md](PRODUCTION.md#первая-установка-запуск-и-диагностика).

## Основа RBAC MVP2-01 (#60)

`GET /api/v1/auth/context` возвращает актуальный контекст четырёх ролей.
JWT идентифицирует пользователя и сессию; роль, активность, подразделение и
разрешения читаются из БД. Межзапросного кеша прав нет. Контекст UI не является
доказательством доступа. Студенческие dependencies и `/users/me` сохранены.

Единый реестр — `app.permissions.PermissionCode`:

| Коды | Независимое действие / область |
|---|---|
| `schedule.edit` | Изменение официального расписания |
| `grades.edit` | Изменение оценок; не предоставляет посещаемость |
| `attendance.edit` | Изменение посещаемости |
| `students.read` | Чтение учебных сведений студентов |
| `students.edit` | Изменение учебных сведений, без изменения статуса |
| `students.status.edit` | Ручное изменение академического статуса |
| `groups.manage` | Управление учебными группами |
| `applications.review` | Обработка заявлений ответственного подразделения |
| `news.publish` | Публикация официальных новостей уполномоченным сотрудником |

Первые семь — учебные права: эффективны только для `staff` подразделения
`dean_office` и явной строки с `scope_org_unit_id=NULL`; охватывают все группы.
Остальные требуют явного scope, равного текущему подразделению сотрудника.
Несовместимые строки не дают доступа; `NULL` вне учебных прав не глобален.
Ни один код не подразумевает другой. Admin не получает предметных прав;
teacher использует назначения из #61, а не `staff_permissions`.

Интерфейсы для последующих задач:

- `require_permission(code)` — dependency учебного действия поверх штатной
  проверки JWT/сессии, возвращает пользователя или `403`.
- `require_staff_permission(db, user, code, org_unit_id=...)` — сервисная
  проверка; для scoped-действий область нужно разрешать из серверных данных.
- `require_application_review(db, user, application_id)` — загружает заявку
  с SQL-фильтром области. Без permission — `403`, чужая/неизвестная — одинаковый
  `404`. Область: `assigned_org_unit_id`, при NULL —
  `service_types.responsible_org_unit_id`; обе NULL запрещают доступ.
- `get_application_scope()` — то же SQL-выражение для очереди #64; очередь
  обязана дополнительно фильтроваться эффективными scope пользователя.
- `get_authorization_context(db, user)` — тот же источник эффективных прав для UI.

Проверки вызывать внутри транзакции предметной операции; состояние объекта,
версии и аудит добавляются владельцами соответствующих задач. Эти интерфейсы
не создают редакторов, преподавательских назначений или административного CRUD.
Сервисные вызовы предполагают пользователя из `get_current_user` (сессия
проверяется dependency); нельзя подставлять ID пользователя из тела запроса.
Для `news.publish` предметный модуль передаёт подразделение издателя, установленное
сервером; scope не задаёт аудиторию новости.

Миграция `20261114_01` добавляет профили/разрешения, CHECK реестра,
FK и два частичных UNIQUE для ненулевой/NULL области. Составной FK профиля к
`users(id, role)` и постоянный CHECK `profile_role` исключают профили разных
ролей, включая прямой SQL и конкурентные записи. Смена роли требует удаления
старого профиля/прав и создания соответствующего нового профиля в одной транзакции;
FK отложен до commit. Существующие teacher без аккаунта остаются допустимыми.
Пользователь без предметного профиля не приобретает прав на операции профиля.
Миграция не создаёт прав или профилей автоматически и не исправляет несовместимые
старые данные: при несоответствии роли профилю установка отклоняется транзакционно.
Существующие профили и ID сохраняются. Перед production upgrade нужна резервная
копия и штатный `scripts/migrate-postgres.sh`: ACL добавляет только SELECT
на две таблицы, без записи и доступа к их sequences. Выдача/отзыв прав — #78;
в #60 отсутствует пользовательский путь самоэскалации.
