# TASK-003 — Общие API-соглашения и генерация TypeScript-типов

## 1. Цель задачи

Создать единую техническую основу взаимодействия backend и frontend Uni Space: общие типы данных и правила API, обработку ошибок, заголовки ответов, cursor-пагинацию, воспроизводимую генерацию TypeScript-типов из OpenAPI и общий HTTP-клиент.

**Задача:** [Issue #4](https://github.com/Panika78/uni-space/issues/4)

**Реализация:** [PR #24](https://github.com/Panika78/uni-space/pull/24)

**Связанные требования:** `REQ-NF04`, `REQ-NF09`; принятый контракт `docs/API.md`, разделы 1–6.

**Итоговый статус по GitHub на 9 ноября 2026 года:** Issue #4 закрыт; PR #24 объединён с `main`. Merge-коммит: [`05d5a1a`](https://github.com/Panika78/uni-space/commit/05d5a1a30f319c4ff0b9c88f357027aad15cc6b3). Сам факт merge не заменяет подтверждение всех проверок.

## 3. Результаты

В рамках TASK-003 реализованы:

- Общие Pydantic-типы для идентификаторов, дат, времени, страниц и параметров пагинации; запрет неизвестных полей в моделях запросов.
- Префикс `/api/v1` с сохранением существующих адресов `/api/docs` и `/api/openapi.json`.
- Единый формат API-ошибок с `error.code`, `error.message`, `error.details`; унифицированные ответы на ошибки HTTP, ошибки валидации и внутренние исключения.
- Заголовки `X-Request-ID` и `Cache-Control: no-store` для ответов API.
- Общая cursor-пагинация с проверкой формата cursor, направления сортировки и составных ключей; тестирование на синтетических данных без создания предметных API-маршрутов.
- Экспорт OpenAPI и генерация TypeScript-типов с командой проверки их актуальности.
- Общий Fetch-клиент, обрабатывающий JSON, HTTP 204, ошибки API, сетевые ошибки и ответы не в JSON-формате.
- Тесты общих соглашений backend и HTTP-клиента frontend.

Обновление зависимостей frontend оформлено отдельным ручным коммитом и не относится к генерации кода ИИ-агентом.

> Проверь воспроизводимость F-09 и F-10, кратко обозначь план и приступай к исправлениям без дополнительного согласования.
>
> **F-09. Middleware скрывает сбой потокового ответа (Medium)**
>
> В `backend/app/core/middleware.py` при исключении после начала отправки HTTP-ответа выполняется:
>
> ```python
> if response_started:
>     log_unhandled_exception(exc, request_id)
>     if not response_complete:
>         await send_with_api_headers(
>             {
>                 "type": "http.response.body",
>                 "body": b"",
>                 "more_body": False,
>             }
>         )
>     return
> ```
>
> Это подавляет исключение и искусственно завершает поток. Клиент может получить неполный ответ со статусом HTTP 200, выглядящий как успешно завершённый.
>
> Существующий тест `test_stream_exception_after_response_start_is_safely_logged_and_not_rethrown` закрепляет неправильное поведение.
>
> Требуется:
>
> 1. Устранить искусственное успешное завершение потокового ответа после исключения.
> 2. Если HTTP-заголовки ещё не отправлены, сохранить полноценный ответ HTTP 500 с единым форматом `internal_error`.
> 3. Если заголовки уже отправлены, не пытаться заменить HTTP-статус на 500 и не отправлять поддельный завершающий блок.
> 4. Обеспечить обнаруживаемое клиентом прерывание неуспешной передачи.
> 5. Сохранить корректную работу обычных успешных и потоковых ответов.
> 6. Не допускать двойной отправки HTTP-заголовков или тела ответа.
