# TASK-007 — Браузерная авторизация и управление сессией

## 1. Цель задачи

Реализовать вход в приложение, восстановление авторизации после перезагрузки страницы, защищённые маршруты, выход из системы и согласованную работу нескольких вкладок.

**Задача:** [Issue #8](https://github.com/Panika78/uni-space/issues/8)  
**Реализация:** [PR #29](https://github.com/Panika78/uni-space/pull/29)

## 2. Использование ИИ

**Инструмент:** ИИ-агенты (OpenAI Codex).

Первоначальная реализация выполнена ИИ-агентом по требованиям TASK-007 и документации проекта. Затем неоднократно проводились независимые ревью, повторные проверки исправлений, аудит безопасности и отдельный анализ производительности. Для SEC-01 дополнительно использовался аналитический промпт, сравнивающий варианты исправления до внесения изменений.

По итогам ревью исправлены замечания **F-01–F-05** и **SEC-01**. Замечание **F-06** принято как низкоприоритетный UX-риск без исправления. Для **SEC-03** реализована дополнительная проверка production-конфигурации, но риск закрыт лишь частично: окончательная защита зависит от будущего развёртывания.

## 3. Результаты

В PR реализованы форма входа, временная защищённая страница `/schedule`, восстановление авторизации через refresh-cookie и хранение access-токена только в памяти. Добавлены координация вкладок через Web Locks, контроль устаревших запросов, очистка кеша после выхода, обработка сетевых сбоев и ограничение повторных запросов.

После аудита SEC-01 согласованы frontend и backend для отзыва сессии при logout без refresh-cookie, когда доступен действующий Bearer. Изменены контракт и документация авторизации.

**Проверки по данным PR #29:**

- Backend: **274** модульных/HTTPX-теста и **108** интеграционных тестов с PostgreSQL — успешно.
- Frontend: **99** тестов Vitest; ESLint, Prettier, TypeScript, production-сборка и проверка API-типов — успешно.
- Реальный браузер: **26 проверок Chromium/Playwright** на этапе исправления SEC-01. После финальных изменений конфигурации SEC-03 браузерный прогон не повторялся; эти изменения проверены отдельно на Uvicorn/HTTP.
- [GitHub Actions #42688966592](https://github.com/Panika78/uni-space/actions/runs/42688966592) на коммите `055508811789` — **9 из 9 jobs успешно**.

**Ограничения:** Firefox/Safari и публичная production-инфраструктура не проверены; полноценные пользовательские API и связанные с ними E2E-сценарии относятся к будущим задачам. SEC-03 частично исправлено; F-06 принято как UX-риск. На момент составления отчёта PR #29 открыт, merge не выполнен.

> Требование: REQ-A02 — безопасное завершение сеанса. При этом API.md разрешает `204` без действующей cookie, поэтому речь не о нарушении формального HTTP-контракта, а о недостаточной гарантии отзыва.
>
> **Доказательства.**
>
> Backend определяет сессию для logout исключительно по refresh-cookie:
>
> ```python
> def revoke_logout_session(db, raw_token):
>     with db.begin():
>         locked = get_locked_refresh_session(db, raw_token)
>         if locked:
>             session, _token = locked
>             revoke_session(db, session, datetime.now(UTC), "logout")
> ```
>
> Если cookie отсутствует либо неизвестна, `locked` равно `None`. Отзыв сессии не происходит, но роут всё равно возвращает `204`.
>
> Frontend воспринимает любой успешный результат как подтверждённый выход:
>
> ```ts
> await apiFetch<void>('/api/v1/auth/logout', {
>   method: 'POST',
>   credentials: 'same-origin',
>   signal: AbortSignal.timeout(15000),
> })
>
> this.writeState({
>   epoch: epoch!,
>   blocked: true,
>   pending: false,
>   ended: true,
> })
>
> this.update('unauthenticated', 'Выход подтверждён сервером.')
> ```
>
> **Сценарий эксплуатации.**
>
> 1. Тестовый пользователь выполняет login и получает access JWT вместе с refresh-cookie.
> 2. Access JWT оказывается у атакующего — это предусмотрено моделью угроз.
> 3. Refresh-cookie исчезает из браузера независимо от действительности access JWT, например после ручной очистки cookies.
> 4. Пользователь нажимает «Выйти».
> 5. Backend возвращает `204`, не идентифицировав сессию и не отозвав её.
> 6. Frontend сообщает об успешном выходе.
> 7. Украденный access JWT потенциально остаётся действительным до окончания собственного срока — обычно до 600 секунд.
>
> **Минимальное безопасное воспроизведение.**
>
> В существующей интеграционной фикстуре `backend/tests/test_auth_integration.py` уже имеются тестовый маршрут `/api/v1/test/user`, два вымышленных аккаунта и HTTPX-клиент. Для дополнительного теста достаточно следующего сценария:
>
> ```python
> @pytest.mark.integration
> def test_logout_without_cookie_leaves_access_valid(auth):
>     client = auth[0]
>     _, refresh_cookie, access = login(auth)
>     # Cookie намеренно не передаётся.
>     response = client.logout(token=None)
>     assert response.status_code == 204
>     # Проверяем оставшийся действительным access.
>     protected = client.request(
>         "GET",
>         "/api/v1/test/user",
>         access=access,
>     )
>     assert protected.status_code == 200
> ```
>
> **Фактический результат аудита:** на тестовой PostgreSQL динамически подтверждено, что logout без идентифицирующей refresh-cookie возвращает `204`, не отзывает серверную сессию, а ранее выданный access остаётся действительным и продолжает получать `200` на защищённом тестовом маршруте.
>
> Последствия: ложная уверенность пользователя в отзыве серверной сессии; при краже access-токена возможно продолжение доступа в пределах остаточного TTL.
>
> Минимальное исправление: согласовать семантику успешного logout с фактическим отзывом. Один вариант — использовать действующий Bearer как дополнительный идентификатор сессии, если refresh-cookie отсутствует. Если контракт намеренно остаётся cookie-only, интерфейс не должен безусловно обещать отзыв сессии по одному `204`; это, однако, лишь исправит сообщение, а не серверную гарантию.
>
> Степень серьёзности — Medium, а не High: сценарий требует одновременно действующего украденного access и отсутствующей/неизвестной cookie. Обычный logout с корректной refresh-cookie отзывает сессию.
>
> **Предложенные варианты исправления:**
>
> **Вариант A — минимальный, без изменения API.**
>
> Сохранить `204` и cookie-only logout. Изменить пользовательское сообщение, например на «Вы вышли из приложения», а в документации явно разграничить успешную обработку logout и подтверждённый отзыв серверной сессии.
>
> Это устраняет вводящую в заблуждение семантику, но не сам риск.
>
> **Вариант B — усилить серверную гарантию.**
>
> Разрешить передавать действующий access JWT как дополнительный идентификатор сессии при отсутствии refresh-cookie.
>
> Тогда сервер сможет проверить `sid`, найти сессию и отозвать её. Понадобятся согласованные изменения API.md, backend и frontend, включая правила выбора сессии, если cookie и Bearer принадлежат разным входам.
