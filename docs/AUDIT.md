# Контракт операционного аудита MVP2

Реализовано в MVP2-29 (#87). Схема — [DB §9](DB.md#9-история-изменений-и-конкурентное-сохранение),
writer — `app.audit.write_audit_event`, модель — `app.models.AuditEvent`.
Это инфраструктура для REQ-G13, REQ-S14, REQ-ADM01 и REQ-ADM05;
предметные операции и страницы истории реализуются своими issues.

## Транзакция и автор

Writer принимает существующую SQLAlchemy `Session`, добавляет событие и вызывает
`db.flush()` для всей единицы работы. Он не создаёт сессию или savepoint,
не вызывает `begin()` / `commit()` / `rollback()` и не подавляет ошибки. Настройки сессии
(`autoflush=False` в приложении) не мешают записи события.

SQLAlchemy использует autobegin: чтение, изменение ORM-объекта или `Session.add()`
могут автоматически открыть транзакцию. Writer проверяет наличие активной
транзакции до добавления события и отклоняет вызов сразу после commit/rollback,
не открывая новую. Но `Session.in_transaction()` не доказывает принадлежность
бизнес-изменения этой транзакции: последующий SELECT уже может открыть другую.
Writer не может восстановить атомарность с ранее зафиксированной операцией.
Границы общей транзакции и порядок вызовов обеспечивает вызывающий сервис;
проверку этого порядка через HTTP необходимо добавить в #69/#72/#74/#78/#79.

Верхнеуровневый предметный сервис проверяет полномочия и область доступа,
изменяет бизнес-данные и вызывает writer **до единственного commit**. При любой
ошибке, включая `ValueError` валидации writer, владелец транзакции откатывает всю
операцию и пробрасывает ошибку. Нельзя ловить ошибку аудита и сохранять бизнес-данные,
писать обязательный аудит в savepoint или выполнять предварительный commit.
Ошибка SQL при flush переводит Session в failed state до rollback.

`actor` — объект `User`, полученный из серверного `get_current_user`, прикреплённый
к той же Session. Writer сохраняет только его `id`. Параметра `actor_user_id`
в интерфейсе writer нет; одноимённое поле во входном снимке игнорируется.
Проверка прикрепления объекта защищает от случайной передачи ID/нового/чужого
объекта, но не заменяет аутентификацию и проверку permissions вызывающим сервисом.
Writer нельзя напрямую выставлять как HTTP-обработчик или вызывать через `**request_body`.

Начальные события ниже требуют пользователя. `NULL` в схеме зарезервирован для
явно описанных будущих системных действий; writer сейчас не принимает `actor=None`.
При добавлении такого действия необходимо явно определить его происхождение,
разрешить NULL только для него и добавить тесты. Подмена пользовательского действия
системным не допускается.

Пример использования в будущем сервисе (права уже проверены, `current_user` и
`user` загружены той же сессией):

```python
from app.audit import write_audit_event

try:
    before = {"is_active": user.is_active}
    user.is_active = False
    write_audit_event(
        db,
        actor=current_user,
        entity_type="user",
        entity_id=user.id,
        action="set_active",
        before_data=before,
        after_data={"is_active": user.is_active},
        reason="administrative_change",
    )
    db.commit()
except Exception:
    db.rollback()
    raise
```

Для новой сущности сначала `db.add(entity); db.flush()`, затем её `entity.id`
передаётся writer в той же транзакции. До изменения сущности нужно сохранить
самостоятельный снимок прежних значений: writer не восстанавливает историю ORM.
При переносе занятия доменный сервис записывает события для изменённой старой и
новой записи и связанные назначения в одной транзакции.

## Начальные события и allowlist

`entity_type` — имя сущности в единственном числе, `action` — действие в `snake_case`.
Пары и поля контролируются `_EVENT_FIELDS` в `app/audit.py`, произвольные значения
не принимаются. Это контракт аудита, а не перечень разрешённых бизнес-операций.

| entity_type | action | Разрешённые поля before/after |
|---|---|---|
| `assessment_result` | `create`, `update`, `delete` | `assessment_group_id`, `student_id`, `score` |
| `final_result` | `create`, `update`, `delete` | `course_offering_id`, `student_id`, `grade_value`, `passed`, `retake_date` |
| `lesson` | `create`, `update`, `cancel`, `move` | `course_offering_id`, `teacher_id`, `starts_at`, `ends_at`, `kind`, `status`, `previous_lesson_id`, `version`, `group_ids`, `room_ids` |
| `user` | `create` | `role`, `is_active` |
| `user` | `set_role` | `role` |
| `user` | `set_active` | `is_active` |
| `student` | `set_academic_status` | `academic_status` |

При `create` before — SQL NULL, after — объект; при `delete` наоборот.
Остальные действия требуют двух объектов с одинаковым набором разрешённых ключей.
Объекты непустые после проекции. Частичные снимки допустимы: домен обязан включить
все изменённые разрешённые поля и необходимые ссылки на контекст. Это не полный
снимок персонального профиля. Отсутствующий ключ отличается от JSON null внутри
объекта. Предметные правила допустимости NULL и переходов проверяет сервис.
`entity_id` — положительный BIGINT ID предметной записи, без универсального FK.
`created_at` задаётся PostgreSQL (`TIMESTAMPTZ DEFAULT statement_timestamp()`):
время начала SQL-команды INSERT события, а не транзакции. Это не время COMMIT
и не гарантия порядка фиксации конкурентных транзакций. Для совпавших времён
`id` обеспечивает детерминированное отображение, а не порядок COMMIT.

Сериализация строится только из allowlist. Неизвестные поля отбрасываются без
обхода их содержимого. ORM-объекты целиком не принимаются. Разрешённые значения:

- ID, баллы, числовая оценка, версия — строго `int`, не `bool`;
- `passed` / `is_active` — строго `bool`;
- даты — `date` в ISO 8601; время — timezone-aware `datetime`, нормализованный в UTC;
- `group_ids` / `room_ids` — плоские списки целых ID с копированием;
- `role`, `academic_status`, `kind`, `status` — только существующие значения из DB.md;
- каждое разрешённое поле может иметь JSON null, если предметный контракт это допускает.

Произвольные словари, вложенные списки, объекты и строки вместо чисел/enum
отклоняются без включения исходных значений в ошибку. Не используется `default=str`.
Нельзя сохранять пароли/хеши, токены, cookie, ключи, файлы и их storage keys, полные
формы заявлений, ФИО, login/email и другие лишние персональные данные.
`reason` nullable; writer принимает только коды `correction`, `administrative_change`,
`schedule_change`, а не свободный текст клиента. Новые коды требуют ревью.
Идентификаторы субъектов и результаты сами являются ограниченно доступными данными.

## Независимое расширение и чтение

Предметная issue добавляет пару и минимальную allowlist с типизированными
сериализаторами в `_EVENT_FIELDS`, документирует её здесь и добавляет тесты
секретов/транзакции. Для нового действия, не являющегося create/delete, действует
контракт двух снимков. Если он не подходит, новое правило формы добавляется явно
вместе с тестами. Не нужны event bus, repositories, регистрация во время HTTP-запроса
или миграция enum в БД. Вызовы writer добавляются в доменных issues: #69 (баллы),
#72 (итоги), #74 (расписание), #78 (администрирование), #79 (академические статусы).
Изменения permissions согласуются с владельцем #60 отдельной интеграцией: этот PR
не меняет роли или механизмы выдачи прав. Production ACL намеренно разрешают только
уже используемые операции API. При подключении первого предметного write API нужно
согласованно расширить `deploy/postgres/privileges.sql`: `INSERT` на `audit_events`,
`SELECT (id, created_at)` для SQLAlchemy `INSERT ... RETURNING`, вместе с правами
записи самого предметного модуля. `id` — IDENTITY, а не SERIAL: генерация значения
при INSERT не требует `USAGE` на `audit_events_id_seq`; прямой `nextval()` требует
права на последовательность и приложению не нужен. Не выдавать
API `UPDATE`/`DELETE` аудита или широкие default GRANT. Предметное чтение при его
реализации потребует отдельного явного SELECT и проверок доступа. Это действие
относится к подключению новых write/read API; существующий MVP1 аудит не вызывает. Жизненный цикл заявлений использует
отдельную `application_history` (#64), не новый тип audit-события.

Публичного универсального read API нет. Предметный read API сначала проверяет
аутентификацию, полномочие чтения истории конкретной сущности и её область доступа
(назначения преподавателя, разрешения сотрудника и т. д.), затем выбирает события.
Знание пары `entity_type/entity_id` или роль admin сами по себе не дают доступ.
Возвращать следует только необходимые поля, с той же allowlist для before/after;
клиент не получает произвольное содержимое JSONB и чужие события. Не следует
выдавать целый ORM-объект или строить фильтр только из присланных ID.

Единственный дополнительный индекс `(entity_type, entity_id, created_at, id)`
обслуживает предусмотренную историю конкретной оценки/занятия/пользователя/статуса
с детерминированным порядком. Глобальные поиски по автору/JSON не реализованы;
дополнительных индексов для них нет. FK автора не удаляет события каскадно и не
обнуляет автора: физическое удаление связанного пользователя блокируется PostgreSQL;
штатная блокировка аккаунта сохраняет автора.

Прямой SQL и прямое создание `AuditEvent` обходят writer: безопасность снимков —
контракт серверного кода, не JSONB-фильтрация в БД. Защиты истории от SQL-администратора,
триггеров автоматического аудита и криптографической неизменности в MVP2-29 нет.
