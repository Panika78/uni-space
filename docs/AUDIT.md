# Контракт операционного аудита MVP2

Реализовано в MVP2-29 (#87), миграция `20261114_02` после RBAC `20261114_01`. Схема — [DB §9](DB.md#9-история-изменений-и-конкурентное-сохранение),
writer — `app.audit.write_audit_event`, модель — `app.models.AuditEvent`.
Это инфраструктура для REQ-G13, REQ-S14, REQ-ADM01 и REQ-ADM05;
предметные операции и страницы истории реализуются своими issues.

## Транзакция и автор

Writer принимает существующую SQLAlchemy `Session`, добавляет событие и вызывает
`db.flush()` для всей единицы работы. Он не создаёт сессию или savepoint,
не вызывает `begin()` / `commit()` / `rollback()` и не подавляет ошибки. Настройки сессии
(`autoflush=False` в приложении) не мешают записи события.

SQLAlchemy использует autobegin: чтение, изменение ORM-объекта или `Session.add()`
могут автоматически открыть транзакцию. Writer проверяет наличие активной
транзакции до добавления события и отклоняет вызов сразу после commit/rollback,
не открывая новую. Но `Session.in_transaction()` не доказывает принадлежность
бизнес-изменения этой транзакции: последующий SELECT уже может открыть другую.
Writer не может восстановить атомарность с ранее зафиксированной операцией.
Границы общей транзакции и порядок вызовов обеспечивает вызывающий сервис;
проверку этого порядка через HTTP необходимо добавить в #69/#72/#74/#78/#79.

Верхнеуровневый предметный сервис проверяет полномочия и область доступа,
изменяет бизнес-данные и вызывает writer **до единственного commit**. При любой
ошибке, включая `ValueError` валидации writer, владелец транзакции откатывает всю
операцию и пробрасывает ошибку. Нельзя ловить ошибку аудита и сохранять бизнес-данные,
писать обязательный аудит в savepoint или выполнять предварительный commit.
Ошибка SQL при flush переводит Session в failed state до rollback.

`actor` — объект `User`, полученный из серверного `get_current_user`, прикреплённый
к той же Session. Writer сохраняет только его `id`. Параметра `actor_user_id`
в интерфейсе writer нет; одноимённое поле во входном снимке игнорируется.
Проверка прикрепления объекта защищает от случайной передачи ID/нового/чужого
объекта, но не заменяет аутентификацию и проверку permissions вызывающим сервисом.
Writer нельзя напрямую выставлять как HTTP-обработчик или вызывать через `**request_body`.

Начальные события ниже требуют пользователя. `NULL` в схеме зарезервирован для
явно описанных будущих системных действий; writer сейчас не принимает `actor=None`.
При добавлении такого действия необходимо явно определить его происхождение,
разрешить NULL только для него и добавить тесты. Подмена пользовательского действия
системным не допускается.

Пример использования в будущем сервисе (права уже проверены, `current_user` и
`user` загружены той же сессией):

```python
from app.audit import write_audit_event

try:
    before = {"is_active": user.is_active}
    user.is_active = False
    write_audit_event(
        db,
        actor=current_user,
        entity_type="user",
        entity_id=user.id,
        action="set_active",
        before_data=before,
        after_data={"is_active": user.is_active},
        reason="administrative_change",
    )
    db.commit()
except Exception:
    db.rollback()
    raise
```

Для новой сущности сначала `db.add(entity); db.flush()`, затем её `entity.id`
передаётся writer в той же транзакции. До изменения сущности нужно сохранить
самостоятельный снимок прежних значений: writer не восстанавливает историю ORM.
При переносе занятия доменный сервис записывает события для изменённой старой и
новой записи и связанные назначения в одной транзакции.

## Начальные события и allowlist

`entity_type` — имя сущности в единственном числе, `action` — действие в `snake_case`.
Пары и поля контролируются `_EVENT_FIELDS` в `app/audit.py`, произвольные значения
не принимаются. Это контракт аудита, а не перечень разрешённых бизнес-операций.

| entity_type | action | Разрешённые поля before/after |
|---|---|---|
| `assessment_group` | `update` | `planned_date`, `lesson_id`, `date_needs_confirmation` |
| `attendance` | `create`, `update`, `delete` | обязательные `student_id` (положительный integer), `status` (`attended`/`absent`) |
| `assessment_result` | `create`, `update`, `delete` | `assessment_group_id`, `student_id`, `score` |
| `final_result` | `create`, `update`, `delete` | `course_offering_id`, `student_id`, `grade_value`, `passed`, `retake_date`, `retake_location` |
| `lesson` | `create`, `update`, `cancel`, `move`, `restore` | `course_offering_id`, `teacher_id`, `starts_at`, `ends_at`, `kind`, `status`, `previous_lesson_id`, `version`, `group_ids`, `participants`, `room_ids` |
| `user` | `create` | `role`, `is_active` |
| `user` | `set_role` | `role` |
| `user` | `set_active` | `is_active` |
| `user` | `change_password` | `credential_changed` |
| `user` | `reset_password` | `credential_reset` |
| `student` | `set_academic_status` | `academic_status` |
| `student` | `create` | `user_id`, `group_id`, `academic_status` (`enrolled`) |
| `teacher` | `link_user` | `user_id` |
| `staff_profile` | `create` | `user_id`, `org_unit_id` |
| `staff_profile` | `set_org_unit` | `org_unit_id` |
| `staff_permission` | `create`, `delete` | `staff_profile_id`, `permission_code` (из `PermissionCode`), `scope_org_unit_id` |
| `news` | `create`, `update`, `publish`, `unpublish` | `title`, `body`, `is_published`, `published_at`, `author_user_id` |

Для `attendance` действует явное исключение: `entity_id=lesson_id`, полный
идентификатор отметки — `(lesson_id, student_id)`, а не один `entity_id`.
Снимок содержит строго `student_id` и `status`; update сохраняет один student_id
и меняет статус. Неизменившийся статус — no-op без события. Для будущего чтения
истории конкретной отметки обязательны предметная ACL-проверка **обоих** ID,
фильтр `entity_type='attendance'`, `entity_id=lesson_id`, action и `student_id`
из before/after. Нельзя выдавать события всех студентов по одному ID занятия.

При `create` before — SQL NULL, after — объект; при `delete` наоборот.
Остальные действия требуют двух объектов с одинаковым набором разрешённых ключей.
Объекты непустые после проекции. Частичные снимки допустимы: домен обязан включить
все изменённые разрешённые поля и необходимые ссылки на контекст. Это не полный
снимок персонального профиля. Отсутствующий ключ отличается от JSON null внутри
объекта. Предметные правила допустимости NULL и переходов проверяет сервис.
`entity_id` — положительный BIGINT ID предметной записи, без универсального FK.
`created_at` задаётся PostgreSQL (`TIMESTAMPTZ DEFAULT statement_timestamp()`):
время начала SQL-команды INSERT события, а не транзакции. Это не время COMMIT
и не гарантия порядка фиксации конкурентных транзакций. Для совпавших времён
`id` обеспечивает детерминированное отображение, а не порядок COMMIT.

Сериализация строится только из allowlist. Неизвестные поля отбрасываются без
обхода их содержимого. ORM-объекты целиком не принимаются. Разрешённые значения:

- ID, баллы, числовая оценка, версия — строго `int`, не `bool`;
- `passed` / `is_active` / `date_needs_confirmation` — строго `bool`;
- даты — `date` в ISO 8601; время — timezone-aware `datetime`, нормализованный в UTC;
- `group_ids` / `room_ids` — плоские списки целых ID с копированием;
- `role`, `academic_status`, `kind`, `status` — только существующие значения из DB.md;
- каждое разрешённое поле может иметь JSON null, если предметный контракт это допускает.

Произвольные словари, вложенные списки, объекты и строки вместо чисел/enum
отклоняются без включения исходных значений в ошибку. Не используется `default=str`.
Нельзя сохранять пароли/хеши, токены, cookie, ключи, файлы и их storage keys, полные
формы заявлений, ФИО, login/email и другие лишние персональные данные.
`reason` nullable; writer принимает только коды `correction`, `administrative_change`,
`schedule_change`, а не свободный текст клиента. Новые коды требуют ревью.
Идентификаторы субъектов и результаты сами являются ограниченно доступными данными.

Изменение/сброс пароля используют события `user.change_password` и
`user.reset_password` в той же транзакции, что запись Argon2id-хеша и отзыв
сессий. Снимки содержат только булевы маркеры `credential_changed` /
`credential_reset`; login, ФИО, пароль, хеш и токены в аудит не записываются.
Runtime ACL для этой операции дополнительно разрешает только
`UPDATE (password_hash)` на `users`.

## Независимое расширение и чтение

Предметная issue добавляет пару и минимальную allowlist с типизированными
сериализаторами в `_EVENT_FIELDS`, документирует её здесь и добавляет тесты
секретов/транзакции. Для нового действия, не являющегося create/delete, действует
контракт двух снимков. Если он не подходит, новое правило формы добавляется явно
вместе с тестами. Не нужны event bus, repositories, регистрация во время HTTP-запроса
или миграция enum в БД. Вызовы writer добавляются в доменных issues: #69 (баллы),
#72 (итоги), #74 (расписание), #78 (администрирование), #79 (академические статусы).
Изменения permissions согласуются с владельцем #60 отдельной интеграцией: этот PR
не меняет роли или механизмы выдачи прав. Production ACL намеренно разрешают только
уже используемые операции API. Предметный write API расширяет
`deploy/postgres/privileges.sql` минимальными правами: `INSERT` на `audit_events`,
`SELECT (id, created_at)` для SQLAlchemy `INSERT ... RETURNING`, вместе с правами
записи самого предметного модуля. `id` — IDENTITY, а не SERIAL: генерация значения
не меняет роли или механизмы выдачи прав. Production ACL в
`deploy/postgres/privileges.sql` для #70 разрешают CRUD `attendance`,
`UPDATE(id)` для блокировок lessons/students/teaching_assignments,
`INSERT` на `audit_events`, `SELECT (id, created_at)` для SQLAlchemy
`INSERT ... RETURNING`, без права чтения снимков аудита.


Изменения permissions согласуются с владельцем #60 отдельной интеграцией: #79
использует существующий реестр и механизм выдачи прав. Production ACL для ручной
смены статуса расширен в MVP2-27: `INSERT` на `audit_events`, `SELECT (id, created_at)`
для SQLAlchemy `INSERT ... RETURNING`, `SELECT` и `INSERT` на отдельный
`student_status_operations` для точного повтора и `UPDATE (academic_status)` на `students`.
Реестр квитанций не является аудитом: хранит только actor/student, target/previous status,
reason и результат, включая no-op, без ФИО, группы или снимков аудита. Runtime не имеет
UPDATE/DELETE на аудит или реестр.
У будущих предметных write API права аудита и таблиц добавляются отдельно и узко.
`id` — IDENTITY, а не SERIAL: генерация значения
при INSERT не требует `USAGE` на `audit_events_id_seq`; прямой `nextval()` требует
права на последовательность и приложению не нужен. Не выдавать
API `UPDATE`/`DELETE` аудита или широкие default GRANT. Предметное чтение при его
реализации потребует отдельного явного SELECT и проверок доступа. Это действие
относится к подключению новых write/read API; существующий MVP1 аудит не вызывает. Жизненный цикл заявлений использует
отдельную `application_history` (#64), не новый тип audit-события.

Для #69 ACL дополнительно включает узкие UPDATE-колонки `students.id`,
`assessments.max_score`, `assessment_groups.id`, `course_groups.group_id` и
`lessons.version`: существующие PostgreSQL-триггеры используют row locks и no-op
родительские UPDATE для сериализации переводов, максимумов и принадлежности работы.
Значения этих полей не меняются write API; остальные колонки сохраняют запрет UPDATE.
Проверка привязки работы к занятию синхронизируется с удалением последней
связи через no-op `UPDATE lessons.version` до чтения `lesson_groups`. Child-row
`FOR SHARE` не используется; runtime-роли не выдаётся UPDATE на `lesson_groups`.

`PUT /teaching/courses/{course_offering_id}/groups/{group_id}/assessments/{assessment_group_id}/results/{student_id}`
(#69) сохраняет только балл заранее утверждённой работы либо `null` для очистки.
Автор и `graded_at` меняются только при изменении значения. Текущие преподавательские
назначение и членство проверяются сервером; сотрудник деканата использует эффективное
`grades.edit` и может корректировать только существующую историческую строку вне группы.
Уникальный ключ результата и блокировка строки сериализуют параллельные записи;
аудит добавляется до commit той же транзакции. Повторное сохранение значения и очистка
отсутствующей строки не создают событие.

Публичного универсального read API нет. Предметный read API сначала проверяет
аутентификацию, полномочие чтения истории конкретной сущности и её область доступа
(назначения преподавателя, разрешения сотрудника и т. д.), затем выбирает события.
Знание пары `entity_type/entity_id` или роль admin сами по себе не дают доступ.
Возвращать следует только необходимые поля, с той же allowlist для before/after;
клиент не получает произвольное содержимое JSONB и чужие события. Не следует
выдавать целый ORM-объект или строить фильтр только из присланных ID.

Единственный дополнительный индекс `(entity_type, entity_id, created_at, id)`
обслуживает предусмотренную историю конкретной оценки/занятия/пользователя/статуса
с детерминированным порядком. Глобальные поиски по автору/JSON не реализованы;
дополнительных индексов для них нет. FK автора не удаляет события каскадно и не
обнуляет автора: физическое удаление связанного пользователя блокируется PostgreSQL;
штатная блокировка аккаунта сохраняет автора.

Прямой SQL и прямое создание `AuditEvent` обходят writer: безопасность снимков —
контракт серверного кода, не JSONB-фильтрация в БД. Защиты истории от SQL-администратора,
триггеров автоматического аудита и криптографической неизменности в MVP2-29 нет.

## Даты работ: общий контракт #71 / #74

`assessment_group/update` использует `entity_id=assessment_groups.id` и полный
снимок трёх полей: `planned_date` (ISO date / NULL), `lesson_id` (integer / NULL),
`date_needs_confirmation` (boolean). #71 пишет отдельное событие для каждого
реально изменённого назначения; повторное сохранение без изменений — no-op.
Изменение нескольких групп и все события фиксируются одним commit; любая ошибка
writer откатывает весь запрос.

#74 использует **то же событие** при установке флага после отмены/переноса пары:
дата и связь сохраняются, before/after отражают фактическое изменение флага.
События занятия и назначений должны находиться в общей транзакции #74.

#71 блокирует выбранные `assessment_groups` и актуальные `teaching_assignments`
в порядке ID, затем новые/сохраняемые `lessons` в порядке ID через FOR UPDATE
NOWAIT. Статус, московская дата и участники проверяются после блокировки пары.
Блокировка удерживается до commit, совместима с родительской блокировкой #62
и `UPDATE lessons SET version=version` существующего триггера. #74 блокирует
занятие до изменения и устанавливает флаг непосредственно связанных назначений
до commit. При обратном порядке блокировок #71 возвращает `409 version_conflict`
с rollback **всего** запроса (`55P03`, `40001`, `40P01`); клиент перечитывает данные.
Автоматического повтора и отдельной версии дат работ нет.

Production ACL разрешает UPDATE только трёх полей назначения, INSERT аудита,
SELECT его `id/created_at` для RETURNING. Identity INSERT не требует USAGE
sequence; прямой nextval запрещён. Для row locks
и существующих триггеров нужны UPDATE `id` у assessments/teaching_assignments,
`group_id` у course_groups и `version` у lessons; предметные поля работ/занятий
не доступны на запись. Изменение версии существующим триггером — присваивание
прежнего значения, без увеличения публичной версии занятия.


## Итоги аттестации (#72)

Новые значения `retake_location` в API — простой текст места (1–200 символов,
без управляющих/служебных Unicode-символов и пустого текста). В поле следует
передавать только место пересдачи, без ФИО, контактов и иных персональных данных.
Writer проверяет строгий тип str и сохраняет исторический PostgreSQL TEXT точно,
даже если он не соответствует новым ограничениям API: длинный/пустой текст и
управляющие символы не обрезаются и не подменяются. JSONB кодирует их как строку;
при отображении потребитель должен экранировать текст, не интерпретировать его
как HTML или команды. `NULL` сохраняется как JSON null, отсутствующий ключ не добавляется.
Изменение только места различимо в before/after (N-02).

Предметный сервис сохраняет все шесть полей снимка. Снятие оценки с известной
пересдачей — update; очистка всех четырёх значений — delete, before содержит
прежнее место, after — SQL NULL. Положительный итог очищает оба поля пересдачи
с аудитом старых значений. Неизменённые значения не создают событие.
Пара `(course_offering_id, student_id)` сериализуется transaction advisory lock,
включая случай отсутствующей строки. При retry заново выполняется вся транзакция
с проверкой актуальных прав; отдельных версий нет.

Доменное событие изменения итоговой аттестации для #86 — зафиксированная запись
`final_result/create|update|delete` в общей таблице. Её `id` служит идентификатором
события, ссылки и значения берутся из before/after. Потребитель читает только
committed-события отдельной транзакцией; до commit ничего не публикуется,
rollback и no-op не создают события. Рассылка и учёт доставки относятся к #86.
Runtime получает INSERT и SELECT(id, created_at) аудита, без UPDATE/DELETE.
Существующий триггер итогов требует UPDATE(id) на course_offerings для FOR SHARE;
права изменения вида аттестации не выдаются.

## MVP2-25: административные действия и первоначальный администратор

Дополнительные строго типизированные снимки:

| entity_type | action | Поля |
|---|---|---|
| `student` | `create` | `user_id`, `group_id`, `academic_status=enrolled` |
| `teacher` | `link_user` | `user_id` (до привязки NULL) |
| `staff_profile` | `create` | `user_id`, `org_unit_id` |
| `staff_profile` | `set_org_unit` | `org_unit_id` |
| `staff_permission` | `create`, `delete` | `staff_profile_id`, `permission_code` (только PermissionCode), `scope_org_unit_id` |

ID — int, academic_status/permission_code — enum. Создание аккаунта использует
существующий `user/create`, активность — `user/set_active`. Перевод сотрудника
создаёт `delete` каждого прежнего grant и `set_org_unit` в одной транзакции.
No-op не пишет событие. Логин, ФИО, пароль, хеш и токены не входят в снимки.

**Единственное исключение для системного актора:** доверенная интерактивная
операторская команда `python -m app.admin.bootstrap` напрямую добавляет
`AuditEvent(entity_type="user", entity_id=<первый admin>, action="create",
actor_user_id=NULL, before_data=NULL,
after_data={"role":"admin","is_active":true})` в той же транзакции с аккаунтом.
Снимок совпадает с allowlist `user/create`. Отказ INSERT аудита откатывает bootstrap.
Обычный `write_audit_event` по-прежнему требует реальный прикреплённый User;
`actor=None` не разрешён. HTTP не предоставляет системный actor или bootstrap.
Это уточняет прежний резерв NULL для будущих системных действий только для этой CLI.

Runtime ACL теперь разрешают append-only INSERT/sequence и SELECT(id,created_at)
для RETURNING. Чтение снимков, UPDATE/DELETE/TRUNCATE аудита по-прежнему запрещены.

## Официальный редактор расписания (#74)

`participants` — строго список объектов с ровно двумя полями: положительный целый
`group_id` и положительный целый либо NULL `subgroup_id`. Снимок сортируется по
группе и подгруппе (NULL первым); дубликаты, bool, строки вместо ID и дополнительные
поля запрещены. Объекты копируются. Поэтому смена подгруппы А→Б различима даже при
неизменном `group_ids`. Произвольные вложенные JSON по-прежнему запрещены.

Операции create/update/cancel/move/restore сохраняют состав участников и аудитории
в снимках lesson. Перенос пишет move старого занятия и create нового. No-op не
создаёт события и не меняет version. Для cancel/move каждое фактическое изменение
флага связанной работы записывается как assessment_group/update с тремя полями
контракта #71; дата и lesson_id сохраняются. Все события и данные фиксируются
единственным commit; ошибка любого writer откатывает всю операцию.

Блокировки: сначала актуальная строка lessons, затем дочерние строки NOWAIT;
#62 уже сохраняет последнюю групповую связь при удалении участников. Миграция
20261116_04 дополнительно проверяет course_groups при SQL-записи участников и
запрещает подтверждение отменённой/перенесённой связи работы. Триггеры касаются
версии строки родителя без изменения значения version, чтобы отвергать устаревший
REPEATABLE READ snapshot. Обратный порядок блокировок при подтверждении #71
может дать 55P03; редактор откатывает запрос и возвращает 409 concurrent_change.
Автоматического повтора с обходом RBAC/version нет.
Миграция 20261116_05 добавляет statement-триггеры публичной версии для прямых
изменений lesson_groups/lesson_rooms. Сервис нормализует версию составной операции
до исходной + 1 под той же блокировкой родителя; аудит снимается после нормализации.
Прямой SQL не создаёт фиктивных событий от имени HTTP-пользователя. Устаревший PATCH
после такого SQL получает 409, не создавая события и не перезаписывая связи.
При неизменном времени move отклоняется без аудита и без пометок работ.

Production ACL разрешают INSERT аудита и SELECT только id/created_at для RETURNING;
UPDATE/DELETE аудита и чтение его payload runtime-роли запрещены. Даты/связи работ,
баллы и посещаемость редактору не предоставляются. UPDATE идентификатора assessments
и ключа course_groups нужны существующим invoker-триггерам для SELECT FOR SHARE;
UPDATE (room_id) у lesson_rooms требуется для FOR UPDATE NOWAIT перед заменой
аудиторий; полное UPDATE таблицы не предоставлено. Значимые свойства работ
не разрешены. Эти GRANT должны сохраняться вместе с
дополнениями #70/#71 при интеграции.

## Предметное чтение оценок и итогов (REQ-G13)

Защищённые GET журнала деканата проверяют действующий `grades.edit` и
предметную пару до выдачи истории. Представление `staff_journal_events`
доступно runtime-роли на чтение и ограничено допустимыми полями снимков
баллов и ручных итогов. Для create источником пары служит `after_data`, для
delete — `before_data`, для update обе пары должны совпадать. Разные
`entity_id` после повторного создания могут относиться к одной истории.
Время и ID автора берутся из аудита, отображаемое имя — из текущей записи
пользователя.

Частичный индекс `ix_audit_events_journal_pair` покрывает поиск по типу,
предметному ID и студенту, затем порядок по времени и ID события. В PostgreSQL
17 на 400 000 синтетических событий запрос одной пары использовал 4 блока и
занял 0,12 мс после добавления индекса. До индекса план проверял 100 000
кандидатов по типу и занял 42,7 мс при том же наборе данных. Значения зависят
от среды и состояния кеша. Производственные ACL сохраняют ограничения
исходной таблицы аудита, включая запрет UPDATE/DELETE.
