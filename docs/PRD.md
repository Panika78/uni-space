# PRD — Цифровой деканат будущего

**Версия:** 1.3 — сокращённая редакция 1.1 с согласованными уточнениями. **Статус:** принятая базовая спецификация; открытые вопросы, `TBD` и предварительные решения требуют отдельного согласования. Реализация задач и приёмка результатов согласуются отдельно.

## 1. Продукт и границы версий

Адаптивное университетское веб-приложение для студентов, преподавателей, сотрудников и системных администраторов. Объединяет расписание, успеваемость, университетские услуги, новости и уведомления. Сокращает переключения между сервисами и повторный ввод информации.

Система поддерживает факультеты, кафедры, направления, образовательные программы, группы, формальные подгруппы, дисциплины, преподавателей и административные подразделения. Функциональность факультетов едина; различия определяются данными и правами. Организационная универсальность не означает обязательную промышленную нагрузку: показатели нагрузки определяются отдельно.

| Этап | Назначение |
|---|---|
| MVP 1 | Работающий студенческий кабинет: вход, профиль, дневное и недельное расписание с изменениями, оценки и сессия, подача и статус заявки, новости, внутренние уведомления, адаптивность и изоляция данных |
| MVP 2 | Взаимодействие ролей: журнал, баллы, посещаемость, учебные работы, редактор расписания с конфликтами, обработка и доработка заявлений, PDF, управление пользователями и полномочиями |
| Extended | Последующее расширение: задачи и их приоритеты перечислены в требованиях ниже |

В MVP 1 допустимы заранее подготовленные вымышленные учебные данные; редакторы расписания и оценок ещё не обязательны. Новые функции добавляются к работающей версии; Extended не задерживает основные версии.

**Обозначения:** P0 — критическое требование конкурсного ядра либо условие корректности выпускаемой функции; P1 — важное расширение; P2 — дополнительная возможность. Приоритет и этап независимы: P0 не обязательно относится к MVP 1. Например, проверка конфликтов P0 выпускается вместе с редактором в MVP 2. Приоритеты, этапы и идентификаторы перенесены из версии 1.1; согласованное исключение — ручное изменение академического статуса (REQ-ADM05) включено в MVP 2.

**Происхождение:** Contest — требование конкурсного задания по классификации версии 1.1; Product — продуктовое решение. Ссылки C-xx сохранены для прослеживаемости; данная редакция не проверяет их по исходному регламенту.

Правила предметной области и описание целевого интерфейса применяются при выпуске соответствующей функции: они не переносят задачи из MVP 2 или Extended в MVP 1. Архитектура, API, хранение данных и стек определяются отдельно. Нерешённые вопросы сохранены в конце; предварительные варианты не считаются утверждёнными.

#### Account rules

- Одна учётная запись соответствует одной основной роли.
- Несколько ролей на одной учётной записи не предусматриваются.
- Быстрое переключение аккаунтов не требуется.
- Самостоятельное восстановление через электронную почту не входит в MVP.
- Студент не может самостоятельно изменять официальные персональные и академические сведения.
- Изменение персональных данных осуществляется через соответствующую университетскую услугу.
- Статус учётной записи не тождественен академическому статусу студента.
- При смене или административном сбросе пароля отзываются все сессии пользователя, включая текущую.
- При блокировке аккаунта все его сессии отзываются; разблокировка не восстанавливает прежние входы.

### 2.2. Access permissions

Базовые роли:

1. Студент.
2. Преподаватель.
3. Сотрудник.
4. Системный администратор.

Назначенные полномочия сотрудника определяют разрешённые действия. Для учебных операций сотрудник деканата с соответствующим разрешением работает со всеми группами независимо от факультета. Обработка заявок по-прежнему ограничена ответственным подразделением и полномочиями.

Правила:

- Сотрудник деканата получает каждую учебную функцию по отдельному разрешению; такое разрешение действует для всех групп, без ограничения факультетом. Само наличие роли сотрудника не даёт всех учебных прав.
- Право работать со всеми группами не расширяет доступ к заявкам: они доступны только уполномоченным сотрудникам ответственного подразделения, в том числе бухгалтерии.
- Ручное изменение академического статуса выполняет сотрудник деканата с отдельным разрешением; системный администратор не получает это право по умолчанию.
- Преподаватель может работать с группами разных факультетов, если ведёт у них дисциплины.
- Администратор не получает автоматически права менять оценки или принимать заявления.
- Пользователь не может расширить собственные полномочия.
- Скрытие элементов интерфейса не считается достаточным разграничением доступа: недоступные действия должны быть запрещены самой системой.

#### Schedule display rules

Правила описывают целевое поведение и применяются по мере выпуска соответствующих функций. Скрытие отменённых занятий (REQ-S06) относится к MVP 2, отображение дополнительных занятий (REQ-S11) — к Extended. Связи нескольких групп в данных MVP 1 не переносят интерфейсную функцию REQ-S07 из MVP 2.

- Расписание отображается по дням.
- У каждого занятия указаны начало и конец.
- Длительные промежутки между занятиями должны быть заметны, но не должны занимать пропорционально большое пространство на мобильном экране.
- Отменённые занятия визуально отличаются от актуальных.
- Перенесённые занятия должны показывать информацию о первоначальном положении и актуальном времени.
- Отменённое занятие не считается занятым временем.
- Внутри свободного окна могут отображаться отменённые занятия.
- Пользователь может скрыть отменённые занятия.
- Скрытие отменённых записей не изменяет расчёт реального свободного времени.
- При наличии нескольких аудиторий без достоверного распределения студент видит все возможные аудитории.
- Система не должна угадывать аудиторию студента.
- Дополнительные занятия отображаются отдельно от официальных, но внутри общего расписания.

#### Schedule and subgroups

К занятию можно назначить одну или несколько учебных групп.

Количество групп не определяется типом занятия: общий семинар может проводиться для нескольких групп так же, как и лекция.

Если существуют формально закреплённые подгруппы, система использует их для определения участников.

Если формального деления нет, дополнительное распределение студентов не создаётся.

#### Conflict detection rules

Базовая проверка является обязательной для редактора расписания.

Система обнаруживает потенциальные конфликты, если:

- Один преподаватель назначен на разные занятия в одно время.
- Одна аудитория используется несколькими несовместимыми занятиями одновременно.
- Одни и те же студенты назначены на пересекающиеся занятия.

**Соприкасающиеся интервалы конфликтом не считаются.**

Например, 10:00–11:30 и 11:30–13:00 не пересекаются.

Для формальных подгрупп:

- Две разные подгруппы одной группы могут заниматься одновременно.
- Два занятия для одной и той же подгруппы могут конфликтовать.
- Если распределение по подгруппам неизвестно, система не должна произвольно предполагать, что участники не пересекаются.

Одно занятие, объединяющее несколько групп, не является конфликтом само с собой.

Для дополнительных занятий допускаются пересечения по времени. Система предупреждает о них, но не запрещает автоматически.

Конфликт физической аудитории должен отображаться независимо от того, является занятие официальным или дополнительным.

#### Concurrent editing

Если два сотрудника открыли одну запись:

1. Первый сотрудник может сохранить изменение.
2. При попытке второго сотрудника сохранить устаревшие данные система предотвращает перезапись.
3. Второй сотрудник получает сообщение, что запись была изменена.
4. Пользователь должен обновить данные перед повторным сохранением.

В MVP 2 достаточно проверки изменений на уровне записи целиком.

Более сложное объединение изменений отдельных полей не требуется.

#### Mass cancellation

При массовой отмене сотрудник:

1. Указывает критерии выбора занятий.
2. Просматривает найденные записи.
3. При необходимости исключает отдельные занятия.
4. Подтверждает отмену.
5. Указывает причину.

После публикации система обновляет расписания затронутых групп и преподавателей и создаёт сгруппированные уведомления.

#### Grading rules

**Баллы:**

- Только целые неотрицательные числа.
- `0` является выставленным результатом.
- «Не выставлено» означает отсутствие результата.
- Отдельное состояние «Не сдавал» не требуется.
- Максимальное количество баллов определяется оцениваемым компонентом.
- Результат не должен превышать предусмотренный максимум; исключений в MVP нет.
- Максимум общий для всех групп работы. Пока не выставлен ни один результат, его можно изменить; после первого результата максимум фиксируется.
- Для баллов, посещаемости, итоговых результатов и параметров работ отдельная защита от перезаписи версиями в MVP не требуется: действует последнее успешно сохранённое изменение с соблюдением предметных ограничений. История изменений оценок сохраняется.

**Посещаемость:**

- Не выставлено.
- Посещено.
- Пропущено.

Преподаватель изменяет посещаемость независимо от баллов.

Студент может быть отмечен как отсутствующий и одновременно получить баллы за работу.

#### Planned assessment source

Запланированные работы первоначально задаются в рамках подготовки учебного периода.

Предлагаемое разграничение:

- Уполномоченный сотрудник может подготовить базовый перечень работ по дисциплине.
- Преподаватель видит эти работы в журнале.
- Преподаватель может дополнять и изменять предусмотренные работы в рамках своих полномочий.
- Для конкурсного прототипа исходные работы могут быть заранее заполнены вымышленными демонстрационными данными.

Полноценный конструктор учебных планов не требуется.

#### Assessment and lesson relationship

Оцениваемая работа является самостоятельной единицей учёта.

Занятие может быть связано с оцениваемой работой, но работа может существовать и без занятия.

Если занятие отменяется:

- Связанная работа не удаляется.
- Баллы не исчезают.
- Дата работы не переносится автоматически.
- Если дата проведения зависела от отменённого занятия, она помечается как требующая уточнения.
- Преподаватель может назначить новую дату или связать работу с другим занятием.

При переносе работы результаты относятся к новой дате её проведения.

Дата выставления оценки не обязана совпадать с датой работы.

#### Multiple groups

Одна контрольная может относиться к нескольким учебным группам.

Преподаватель может изменить дату и связь общей работы с занятием для всех выбранных групп или только для части из них. Название, тип, описание и максимальный балл остаются общими для всей работы; изменение общих свойств требует прав на все затрагиваемые группы. Максимум после первого результата не изменяется.

Не требуется заново создавать одинаковую работу для каждой группы.

### 2.8. Examination session

Отдельного раздела «Сессия» в основной навигации нет.

Информация о сессии находится в разделе «Успеваемость» под текущими дисциплинами.

Поддерживаемые виды аттестации:

| Type | Result |
|---|---|
| Экзамен | 2, 3, 4, 5 |
| Зачёт | Зачтено / Не зачтено |
| Дифференцированный зачёт | 2, 3, 4, 5 |

Шкалы аттестации утверждены: экзамен и дифференцированный зачёт — 2–5; зачёт — «Зачтено» / «Не зачтено». Отсутствие результата означает «Не выставлено» и само по себе не является задолженностью.

Преподаватель выставляет итоговый результат вручную.

Автоматический расчёт итоговой оценки из баллов не входит в основную функциональность.

Студент видит актуальный результат, задолженность или назначенную пересдачу.

Полноценная история всех попыток сдачи не требуется в пользовательском интерфейсе.

История изменения итогового результата сохраняется для контроля корректировок.

#### Application states

Решение по заявлению и готовность документа учитываются отдельно.

**Состояния рассмотрения:**

- Отправлено.
- В работе.
- Требует исправления.
- Повторно отправлено.
- Одобрено.
- Отклонено.

**Состояния документа:**

- Не требуется.
- Ожидает формирования.
- Готов.
- Ошибка формирования.

Не каждое заявление обязательно приводит к выдаче PDF.

Одобрение заявления не должно автоматически означать, что документ уже сформирован.

Сбой формирования PDF не отменяет одобрение. Для одобренной заявки с ожидающим или неудачным формированием доступен явный повтор; повторный запрос уже готового документа возвращает прежний PDF и не создаёт новый. После отказа по заявлению интерфейс не обещает выдачу документа, даже если технический статус документа остался «Ожидает формирования».

#### Application correction

Если сотрудник возвращает заявление:

1. Указывает причину.
2. Студент получает уведомление.
3. Заявление переходит в состояние «Требует исправления».
4. Оно перестаёт находиться в активной очереди рассмотрения.
5. Студент исправляет необходимые данные или вложения.
6. Повторно отправляет заявление.
7. Заявление возвращается в рабочую очередь.
8. История сохраняется.

Новый номер не создаётся.

При создании заявки кнопка отправки блокируется на время запроса. Если ответ потерян, интерфейс предлагает проверить список заявок перед повторной отправкой. Серверная защита от повторной отправки одной операции — P2, не блокирует MVP; повторные самостоятельные заявки на ту же услугу допустимы.

Полноценная переписка внутри заявления отсутствует.

#### Attachments

Предлагаемые ограничения для первой версии документооборота:

- Форматы: PDF, JPG, PNG.
- Максимум 5 файлов на обращение.
- До 10 МБ на файл.
- Возможность замены файлов при доработке.
- Доступ к вложениям только для заявителя и уполномоченных сотрудников.

Числовые лимиты являются предварительными и могут быть уточнены до реализации.

История всех предыдущих версий вложений — P2.

#### Document immutability

**После выдачи PDF сохраняется как неизменный документ.**

Изменение персональных данных студента не должно автоматически изменять ранее выданные справки.

Для получения документа с обновлёнными данными создаётся новый запрос.

Все документы имеют заметную отметку о демонстрационном характере.

**Конкретный сценарий PDF после одобрения:**

Студент запрашивает демонстрационную справку из бухгалтерии об отсутствии задолженности по оплате обучения.

Сотрудник бухгалтерии проверяет обращение в пределах демонстрационных данных и одобряет его.

9. Импорт сторонних личных календарей.
10. Двусторонняя синхронизация календарей.
11. Полноценный финансовый кабинет.
12. Реальные денежные переводы.
13. Юридически значимый документооборот.
14. Интеграция с настоящей пропускной системой.
15. Мессенджер между студентами и сотрудниками.

## 4. Навигация и интерфейс

Визуальный стиль не утверждён: рассматриваются академический минимализм и современный digital workspace. Интерфейс сдержанный и без перегрузки. На компьютере — боковое меню, на телефоне — верхняя панель с бургер-меню; имитация нативного приложения не требуется. Основные разделы доступны за 1–2 перехода. Отдельная главная необязательна.

| Роль | Стартовый экран и навигация |
|---|---|
| Студент | Расписание текущего дня. Разделы: расписание, успеваемость, услуги и документы, новости. Профиль — в меню пользователя, настройки — в профиле, уведомления — через колокольчик |
| Преподаватель | Журнал или расписание — решение TBD. Основные разделы: расписание и электронный журнал; объявления создаются в контексте дисциплин |
| Сотрудник | Стартовый экран соответствует обязанностям, например очередь заявок. Разделы доступны по полномочиям |
| Администратор | Стартовый экран — пользователи; дополнительные разделы управления — по полномочиям |

**Профиль:** ФИО, фотография или аватар, факультет, направление, программа, курс, группа, академический статус и настройки. Официальные сведения студент самостоятельно не меняет.

**Расписание:** компактный дневной просмотр, переключение недель, различимые занятия и временные промежутки. Длинные окна сжаты; на телефоне нет избыточных пустых областей. Пересекающиеся занятия не скрывают друг друга. Остальные правила отображения — в разделе расписания.

**Успеваемость:** текущие дисциплины → сводные результаты → сессия; ссылка на архив предыдущих семестров — внизу после выпуска функции архива. Информация внутри дисциплины доступна без перебора недель расписания.

**Заявки:** форма обозначает обязательные поля, объясняет необходимые документы, проверяет ввод, подтверждает отправку и показывает актуальный статус. Правила доработки и документы определены в разделе услуг.

**Уведомления:** заметные, краткие, конкретные, без избыточных сообщений. Критические изменения видны также в соответствующем разделе продукта.

**Общие состояния:** загрузка, отсутствие данных, ошибка, успешное действие, недостаточно прав, изменение информации. Основные сценарии работают от 360 px без критической горизонтальной прокрутки, доступны с клавиатуры; важный смысл не передаётся исключительно цветом.

**Демонстрационный QR-пропуск — P2:** карточка в профиле связана с аккаунтом, не раскрывает чувствительные данные и обозначена как демонстрационная. Проверка пропуска, сканирование для прохода и турникеты не реализуются.

## 5. Приёмка

### MVP 1

MVP 1 считается завершённым, если:

- [ ] Доступна публичная ссылка на прототип.
- [ ] Студент может войти и выйти.
- [ ] Подготовлены два студенческих аккаунта.
- [ ] Профили и академические данные различаются.
- [ ] После входа открывается расписание.
- [ ] Можно просмотреть день и неделю.
- [ ] Видны аудитории, преподаватели и изменения.
- [ ] Доступны оценки, зачёты и результаты сессии.
- [ ] Можно создать заявку.
- [ ] Заявка сохраняется и имеет статус.
- [ ] Есть раздел официальных новостей.
- [ ] Доступны внутренние уведомления.
- [ ] Персональные данные пользователей изолированы.
- [ ] Основные сценарии работают на ширине от 360 px.
- [ ] Сайт явно обозначен как конкурсный прототип.
- [ ] Приложение открывается из России без VPN.

### MVP 2

MVP 2 считается завершённым, если:

- [ ] Преподаватель может открыть журнал своих групп.
- [ ] Работает выставление целочисленных баллов.
- [ ] Работает учёт посещаемости.
- [ ] Изменения результатов отображаются студенту.
- [ ] Есть история изменения результатов.
- [ ] Преподаватель может изменить дату контрольной.
- [ ] Сотрудник может создавать и редактировать официальные занятия.
- [ ] Базовая проверка конфликтов работает.
- [ ] Конкурентное редактирование занятий и заявок не приводит к незаметной потере изменений; для оценок действует последнее успешно сохранённое изменение с аудитом.
- [ ] Отмена и перенос занятий создают соответствующие уведомления.
- [ ] Сотрудник может обработать заявку.
- [ ] Заявление можно вернуть на доработку.
- [ ] Студент может исправить и повторно отправить заявление.
- [ ] Шаблонная справка формируется автоматически.
- [ ] После одобрения соответствующего запроса формируется PDF.
- [ ] Выданный PDF остаётся неизменным.
- [ ] После сбоя формирования можно повторить выдачу PDF без дубликатов и без отмены одобрения.
- [ ] После смены или сброса пароля все прежние сессии недействительны.
- [ ] После первого результата максимум работы не изменяется.
- [ ] Одобрение заявления на академический отпуск не меняет статус автоматически; уполномоченный сотрудник деканата может изменить его вручную с аудитом.
- [ ] Административные операции ограничены полномочиями пользователей.
- [ ] Подготовлены тестовые аккаунты реализованных ролей.

### Общая проверка

Изменения сохраняются после перезагрузки и повторного входа. Все предусмотренные базовые тестовые случаи конфликтов обнаруживаются. Пользователь не может получить чужие защищённые данные или выполнить действие другой роли; проверяется и прямой доступ, а не только видимость элементов интерфейса. Основные сценарии доступны с телефона. Соответствующие проверки применяются на этапе выпуска функции.
